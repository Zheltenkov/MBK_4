```powershell

```

Сохранить Markdown или JSON:

```powershell
.venv313/Scripts/python -m analytics.production_leads --output ОТЧЁТ_ЛИДЫ.md
.venv313/Scripts/python -m analytics.production_leads --format json --output logs/production-leads.json
```

Доступные параметры: `--days` (1–90, по умолчанию 8), `--recent-hours`
(1–168, по умолчанию 60), `--grace-minutes` (по умолчанию 60),
`--host`, `--port`, `--database`, `--user`, `--access-file`, `--format`, `--output`.
Для смены хоста также есть MBK_REPORT_HOST. MBK_REPORT_PASSWORD может
передаваться через защищённое окружение процесса вместо файла; пароль не
передаётся аргументом CLI, не выводится и не сохраняется в отчёт.

Код: `analytics/production_leads.py`; фиксированные SQL:
`analytics/lead_report_queries.py`. Ввод произвольного SQL не предусмотрен.
Код не зависит от временной папки Claude.

## Что защищает режим чтения

- Startup option `default_transaction_read_only=on` действует до первого SELECT.
- Дополнительно conn.read_only=True и проверка server transaction_read_only=on.
- Восемь разделов используют одну REPEATABLE READ транзакцию и один timestamp БД.
- statement_timeout=20 секунд, lock_timeout=3 секунды, connect_timeout=10 секунд.
- Только зарегистрированные SELECT, без POST, INSERT, миграций и тестовых лидов.
- Не извлекаются тексты переписки, ФИО, номера телефонов или last_error с ПД.
- Роль mbk_app — роль приложения; подтверждён режим этой транзакции,
  а не утверждение, что права самой роли ограничены SELECT.

## Значение разделов и отличия от старых скриптов

1. **daily** — восемь календарных дат МСК с нулевыми днями; уникальные сессии
   отправки, наличие CRM ID, локально завершённые анкеты и события ошибок.
   Старый скрипт брал скользящие 8 суток и мог показывать девятую неполную дату.
2. **month** — календарный месяц МСК и подтверждённый lead_id. Это число
   отправленных ботом лидов, не количество оплаченных/принятых партнёром.
3. **latest** — время и lead_id из одной строки события; не независимые max
   по времени и ID, которые могли бы относиться к разным отправкам.
4. **hourly** — лиды и ходы сегодня по МСК.
5. **recent_cohort** — сессии, созданные за последние 60 часов, а не все
   отправки за эти даты; написали = есть реальная client-реплика. Прежняя
   проверка длины истории могла учитывать служебные/ботовые сообщения.
6. **crm_failures** — за 72 часа только stage/reason, без свободного last_error.
7. **phone_without_lead** — до 50 кандидатов старше часа по созданию,
   с total_candidates, сценарием/статусами и признаком отмены. Это не доказанные
   потери: бывают existing/off_topic, ожидание consent и продолжающаяся анкета.
   Возраст сессии не равен времени молчания клиента.
8. **coverage** — границы сохранившихся analytics_events и sessions.

`qualification_completed` — локальное завершение, не фактическая категория CRM.
`submitted_with_crm_category` берётся из сохранившегося crm_workflow при наличии
события отправки. Сессии удаляются по retention: этот разрез не позволяет
восстановить категории за весь месяц. `landing_group` — исторический landing,
не достоверный адрес текущей страницы; other_or_unknown включает неизвестные.
Числа дневных отправок и когорт сессий напрямую между собой не делить.
