## 1. Цель и границы

Цель — использовать уже собранные сведения, вести человека по нужному
сценарию и доводить обращение до согласия/доставки без повторного телефона
на партнёрском онлоадере и без лишних лидов.

Входы: явный запрос клиента, очищенный контекст входа, подтверждённая текущая
анкета/состояние обращения, действующий результат CRM и согласие по офферу.
Выходы: standard/debt-политика диалога, факты с источником, подтверждённое
согласие, один владелец доставки и наблюдаемый исход либо честное ожидание/ошибка.

Один оркестратор в существующем ядре. Коммерческие правила остаются
детерминированными, LLM извлекает и формулирует. Замена классификатора,
новый провайдер, RAG и автономные агенты в этот объём не входят.
Применимость юридической процедуры не выводится только из долга/имущества.

Урегулирование пока не требует отдельной платформы. Долговое предложение
остаётся БФЛ: списание/реструктуризация. МФЦ пока вне первого сценария.
Кредит/МФО допускаются в общем каталоге для явного соответствующего запроса;
это не автоматический запасной путь для долгового клиента.

## 7. Предлагаемые контракты и состояния

Названия ниже обозначают проектные контракты. Часть read-context/questionnaire
реализована по ADR-0004/0005; это не имена готовых публичных API МБК.

| Контракт | Содержание | Владелец |
|---|---|---|
| EntryContext | source, product_hint, allowed page, защищённая связь с обращением | adapter + server policy |
| SiteContextSnapshot | факты/происхождение/давность, contact_known, request/lead reference, права | backend adapter |
| QuestionnairePolicy | standard/debt, version/reason, вопросы/derivation/contact policy | детерминированный domain |
| DeliveryContext | bot/site_backend, request reference, уже созданный lead, разрешённая операция | orchestration + backend |
| ConsentEvent | offer/version, решение/время, source reference, event dedup key | consent adapter |
| DeliveryOutcome | accepted signal, queue, confirmed/rejected/unknown, receipt | backend + monitoring |

Переходы: entry → resolving_context → context_ready → collecting_missing →
offer → awaiting_consent → submission_pending → submitted/rejected/unknown.
Для обычного нового обращения resolving_context может закончиться разрешённым
режимом new_user. Ошибка доступа не преобразуется в найденную анкету.

При delivery_owner=site_backend submission_pending означает сигнал backend,
а не наш lead-intake. Generic existing/off_topic/cancel-policy сохраняется.
Qualification, получение consent и доставка — разные события и доказательства.

  онлоадер с известным контактом. Для каждого известен один владелец доставки.
- [ ] Чужой/просроченный handle, неизвестный источник, нет данных, stale,
  timeout/5xx, повторная вкладка/перезагрузка и восстановление процесса.
- [ ] На известном контакте онлоадера — ноль вопросов о телефоне и ноль
  дополнительных lead-intake. При недостаточных правах — ноль выдач данных.
- [ ] Нулевой/неизвестный доход, неизвестное авто/регион/история,
  долг без активных кредитов, границы 189999/190000/299999/300000.
- [ ] Consent no/pending/yes, несовпадение оффера, повтор/поздний callback,
  unknown outcome, отказ/отмена; отсутствие ложного текста «отправлено».
- [ ] Консультация без гарантий, без выдуманного партнёра/URL/фактов;
  отдельный проверенный корпус и regression standard/entry/PII.
- [ ] События: context lookup/result, policy selection/reason, известный
  контакт/повторный вопрос, показ оффера, явное согласие, receipt и доставка.
  Версии source/schema/model/prompt/rubric/build, latency/cost и recovery.
- [ ] В аналитике нет телефона, ФИО, диалога, raw form-id или URL с query.
  Источник/канал и определение уникальной отправки сохраняются.
- [ ] Поля local match, category CRM, lead_id, recipient delivery, consent,
  договор и подтверждённая оплата считаются раздельно.

Будущие Python-правки: проверить конфиг и пройти штатные
`.venv313/Scripts/python -m ruff check .`, `-m pyright`, `-m pytest`.
Изменённый site_widget — свои npm tests; фронтенд — проверки package.json.
Первый этап меняет код и проверяется отдельными HTTP/model/coordinator тестами
и source mutation suite. Прежние 104 теста не доказывают новые сценарии.

## 9. Пилот и эксперименты

Сначала стабилизировать интеграции и собрать сопоставимый baseline.
41% и почти 46% — сообщения Михаила, не наш пересчёт и не A/B.
Договоры — обратная связь о примерах результата, не измеренная выручка.

Потом раздельно планировать: стандартная/долговая анкета; варианты первого
экрана/приветствия; страница согласия/согласие в чате. Если меняем пакет целиком,
измеряем эффект пакета, не приписываем его переносу телефона или одной кнопке.

Eligible-когорты и ключ единицы фиксируются до воздействия, назначение
устойчиво. Новый посетитель и partner-resume/onloader не смешиваются без
разделения. Контроль и вариант получают одинаковые общие исправления.
Определения уникальности/согласия согласовать с отчётом Михаила; основной
конечный результат и окно выбрать до запуска, не менять по красивой цифре.

До старта: p0, полезный эффект, мощность/выборка, max-duration, latency/cost/error
лимиты и остановка при дубликате/ложном согласии/утечке. Две недели не гарантируют
достаточности данных. Неизвестные исходы не исключаются из назначенной группы.
Rollback не повторяет отправку и сохраняет привязку действующих сессий.
Push/MR, включение трафика и production-тесты требуют текущего поручения.

## 10. Что пока не входит в первый запуск

- Отдельная платформа урегулирования и подключение нового сервиса под неё.
- Автоматическая альтернативная поставка RF-02 без контроля существующих исходов.
- Вся витрина, переключатель мессенджеров и полная история обращений CRM.
- Запуск всех новых направлений матрицы: кредит/МФО включить в проект каталога,
  реальные условия/партнёров и consent подтвердить до активации.
