Боевой контур МБК (выяснено 18.08.2026, разбор жалобы «а когда ссылка появляется?»):

- Текущий GitLab проверен 02.11.2026: `https://gitlab.mbk-credit.ru`,
  `mbk/mbk_ai` ID 4, ветка main, код внутри custom/vendor-src. Ведёт
  бэкенд-разработчик Андрей Васин. Успешный вход под v.zheltenkov;
  пароль/cookies не сохранялись. Карта репозиториев/доступа — [[gitlab-access-map]].
  Старый хост и numeric ID не использовать для операций без повторной сверки.
- **Окно чата на сайте — их собственный виджет, не наш интерфейс.** Наш
  `mbk-frontend` работает у них как обратный прокси к боту: подключён к сети
  сайта под именем `mbk-chat`, nginx сайта проксирует на него `/chat-api/`.
  Клиент наш React-интерфейс не видит.
  Практическое следствие: всё, что видит клиент, должно приходить **текстом
  пузыря**. Кнопки, статус-бары и прочие элементы нашего UI до него не доходят —
  именно на этом сгорела формулировка «ваше решение по кнопке ниже».
- Образы у них в собственном registry `pipe.mbk.ru:5000`, теги задаются в
  `docker-compose.override.yml` поверх нашего `docker-compose.yml`.
- Виджет стоит на рекламных лендингах и передаёт метки `utm_*`/`landing` при
  создании сессии. С версии 1.0.2 это поддержано нативно (`attribution.py`), до
  того у них был свой патч-слой `custom/patched/`.

**Почему:** ничего из этого не видно из нашего репозитория — узнаётся только
через их GitLab, и без этого правки в UI-части делаются вслепую.

**Как применять:** любое сообщение клиенту проверять на «видно ли это в чужом
виджете»; изменения возить через ветку `dev` и MR, `main` не трогать.

## Переписка о российском промежуточном узле, 09.11.2026

Пользователь передал переписку8–9 ноября. Андрей связал предполагаемую блокировку
другого сайта с туннелем к зарубежному серверу бэкапов. Причина остаётся гипотезой
участников. В09.11 11:12 сообщено решение арендовать дешёвый сервер и направлять
доступ через него. Предложенная перед этим цепочка для ИИ-бота включает отдельный
российский промежуточный сервер перед зарубежным узлом.

Статус — сообщённое решение заказчика. Адрес нового сервера, конкретный транспорт,
ответственный, готовность и фактическое подключение ещё требуют уточнения.
Резерв полного приложения с БД обсуждается отдельно от промежуточного сетевого узла.

Локально09.11 проверены `config.py:_read_proxy_urls` и `transport.py:_new_connection`.
Приложение принимает HTTP/HTTPS CONNECT-прокси через `OPENROUTER_PROXY`, допускает
несколько адресов для переключения. Последовательную цепочку нужно обеспечить
на стороне промежуточного узла. Список адресов в приложении задаёт запасные пути.
Точный боевой маршрут по этой проверке ещё требует сверки.

## Правило передачи и локальная Polza, 11.11.2026

Пользователь запретил прямой доступ к боевому серверу. Изменения готовятся
в dev, перед отправкой показываются состав и короткие сообщения коммитов.
После согласования передаются через MR Андрею — [[deploy-process]].

Пользователь уточнил текущий объём переноса на Polza как локальную Нику.
Выбран прямой API https://polza.ai/api/v1. Ключ лежит в игнорируемом .env,
переменная POLZA_API_KEY, выбор сервиса MBK_LLM_PROVIDER=polza.
Кабинет Polza содержит пользовательский ключ Nika_api. Пароль кабинета
в рабочие документы не сохраняется. Ключи и доступы в Git не помещать.

Локальный launcher расположен в AppData/Local/MBK-local-live-chat/run_chat.py,
он выбирает модельные настройки из .env и отдельно блокирует бизнес-адаптеры.
Инструкция для администратора — docs/INSTALL.md. Данные проверки и прежняя
конфигурация для отката находятся в AppData/Local/MBK-polza-migration/.
Прямая проверка API, SSE, обоих извлекателей и native JSON schema пройдена.
Проверены5 ходов обычной и долговой беседы, сохранение отказа и known400000.
