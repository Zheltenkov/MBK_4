Матрица правил в CRM заказчика составлена под значения, которые шлёт **форма на
сайте**, а не под полный справочник Битрикса. Значение вне этого словаря
условие правила не проходит, и лид уходит в «Не прошёл квалификацию». Мы этого
не знали и слали коды справочника целиком; заказчик поправил `crm_mapping.py`
сам 27.08.2026 (сборка 1.0.7-mbk1), правку мы приняли — см.
[[mbk-patches-vendor-src]].

Действующий словарь:

- кредитная история — только `9255` (нет просрочек) и `9257` (есть просрочки);
  выводится из ответов про кредиты и просрочку, как `deriveCreditHistory` их
  анкеты, а не отправляется фактом напрямую;
- занятость — только `3082` (найм), `377` (самозанятый), `378` (не работаю);
- «нет просрочки» уходит явным `22606` (`OPTION_DELAY_NONE`), раньше уезжало
  пустым полем.

**Три места, где маппинг по-прежнему передаёт не то. Пользователь 27.08.2026:
«пока оставь, но запомни» — то есть чинить только после ответа Андрея.**

1. **Клиент, прямо просящий банкротство, уезжает как «нет просрочек».** При
   `credit_history = ready_bankruptcy` и неизвестной просрочке (или ответе
   «действующих кредитов нет» — обычное дело, когда долги просужены или
   проданы) вывод даёт `9255`. Проверено прогоном на боевом маппинге. Ветка
   «история непустая, но не has_overdue» падает в оптимистичную сторону, а
   правка делалась ровно ради этого клиента. Честнее `9257`.
2. **Двухсловное ФИО разбирается позиционно и ошибается.** «Иван Петров» даёт
   фамилию `Иван`, «Иван Петрович» — фамилию `Иван` и имя `Петрович`, фамилии
   нет вовсе. Трёхсловный вариант разбирается верно. Рядом в том же файле уже
   лежит `_is_likely_patronymic` — им и различать «Имя Отчество» от «Фамилия
   Имя».
3. **Пенсионер уезжает как «не работаю»**, а «свой бизнес» и «самозанятый»
   слиты в один код. Для маршрутизации неважно, но оператор в карточке видит не
   то, что человек сказал. Уточнить, правда ли в их справочнике только три
   значения.

Факты сессии ни одна из этих правок не меняет — расхождение живёт только на
границе с CRM.

**С 31.08.2026 имена полей квалификации — только битриксовые.** Коммит
18490d4d в `mbk/crm-mbk` («#97878 Новая партнёрка») удалил анкетный формат
входа `first-qualification`. Теперь оба запроса, `first-qualification` и
`realty-qualification`, читают те же Битрикс-поля, что `lead-intake`
(`CrmLeadProfileMapper::toProfile`). До 14.09.2026 наши
`FirstQualificationRequest` и `RealtyQualificationRequest` слали анкетные
ключи. CRM их не видела, профиль был пустой, категория `null` у каждого лида.

Починено 14.09.2026: запрос квалификации — срез запроса лида, те же имена,
типы и функции расчёта; живая проба дала категории 2217 и 21300. Тесты
`tests/test_crm_qualification_contract.py` падают, если поле квалификации
разойдётся с полем лида.

**`CHAT_OWNER` — только при частной собственности.** Если указан собственник,
а `UF_FORM_OF_OWNERSHIP_FLAT` не передан, CRM считает объект частным (4671).
Кода муниципальной формы у нас нет. Поэтому для объекта, не подтверждённого
частным, собственник не уходит ни в один из трёх запросов. Вопрос Андрею —
код муниципальной формы.

Правила сопоставления в `RuleMatcher`:
- условие, не заданное в правиле, не ограничивает;
- заданное условие при пустом значении профиля не выполнено;
- исключение — наборы, где правило разрешает «Пустое поле».

Какие поля читает профиль:

| Поле профиля | Битрикс-поле |
|---|---|
| сумма | `SUMM` |
| возраст | вычисляется из `BIRTHDATE` |
| долг | `UF_DEBT_SUMM` |
| есть недвижимость | `UF_REALTY_CC_4_22` = 4697 |
| регион проживания | `UF_CRM_1452153725` |
| тип объекта | `UF_CRM_1452154011` |
| регион объекта | `CHAT_REALTY_REGION` |
| собственник | `UF_PROPERTY_OWNER_FLAT`, иначе `CHAT_OWNER` |
| форма владения | `UF_FORM_OF_OWNERSHIP_FLAT` |
| авто | `UF_HAVE_AUTO`, `UF_CAR_PRODUCTION_YEAR_1..3`, `UF_CREDIT_AUTO_1..3` |
| кредитная история | `UF_CREDIT_HISTORY` |
| просрочка | `UF_CRM_LOAN_OVERDUE_DURATION` |
| занятость | `UF_CRM_1460622474` |

Код классификатора — `lara/app/Services/Classification/`, правила — таблица
371.
