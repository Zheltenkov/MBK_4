# ADR-0003: Локальная цепочка с настоящим Битриксом

Дата: 06.11.2026. Статус: принято; изолированный native-прогон выполнен с явным
восстановлением отправки. [Результат и границы](../../dev/mbk-local/NATIVE-RESULT.md)
фиксируются отдельно; автоматический handoff не объявляется подтверждённым.

Пользователь запросил создание настоящего лида в локальном Битриксе и передачу
в локальную партнёрку без боевых отправок. Режим protocol_simulation из ADR-0002
проверяет wire-контракт и не удовлетворяет этому критерию. Готовой обезличенной
базы МБК нет.

Используем новую официальную демо-установку Битрикс24, установленную штатным
мастером без регистрации у поставщика, переноса боевого ключа и изменения
лицензионных проверок. Предыдущая попытка на закреплённом исходном коде CRM
сохраняется отдельно: она вернула перенаправление на активацию, а не создала лид.
Версия официального ядра отличается от снимка МБК; это явная граница проверки.

Сайт и Laravel CRM/партнёрка выполняются из закреплённых исходников МБК без
изменения бизнес-кода. На границе native Битрикса допускается небольшой
лабораторный HTTP-адаптер, вызывающий настоящие CCrmLead::Add/Get/Update и
API пользовательских полей. Он сопоставляет legacy enum-коды сайта с ID новой
локальной установки. Это native API harness, не исходный customer receiver,
не проверка Bitrix REST OAuth и не проверка боевых роботов/бизнес-процессов.

Целевая последовательность: обычные session/CSRF запросы к сайту → один
штатный ProcessSendLeadBfl → штатный CRM-контроллер → native Add и чтение
сохранённого лида → штатный SendLeadMicroservice → HTTP-контроллер партнёрки →
выбор кампании → один LeadSend → локальный тестовый получатель. ID сайта,
native Bitrix ID и внутренний ID партнёрки различаются; корреляция выполняется
по явному run ID и полю партнёрки lead_id.

Партнёрка использует новую пустую схему. Искусственные настройки кампании,
баланс и справочники разрешены; leads, sent, очередь распределения, история
доставки и списания не создаются фикстурами. Они должны появиться через
штатный поток. Возраст, география, пороги и локальные настройки фиксируются
как условия конкретного теста, а не как подтверждённая выгрузка production.

Все runtime подключены только к internal Docker network, без host ports,
прокси и доступа к Docker socket. Рабочие процессы запускаются только по
одному в выделенной очереди с ограничением времени. Старые контейнеры,
ожидающие/ошибочные jobs и volumes сохраняются. Исходящий SMTP отключён;
автоматизация Битрикса ограничивается лабораторным контуром, а штатные записи
его установщика сохраняются и учитываются.

Приёмка требует native API read сохранённых полей и того же Bitrix ID у
партнёрки и в HTTP receipt получателя; native sent/history, изменения очереди
и тестового баланса проверяются независимо. HTTP2xx означает только ответ
локального получателя. Ни реальная компания, ни клиентский договор, ни
производственная конверсия этим прогоном не подтверждаются.

При ошибке сохраняем наблюдаемое состояние и артефакты. Нельзя очищать
очередь/таблицы, подменять ID или повторять отправку вслепую. Для остановки
используются stop соответствующих новых сервисов без удаления volumes.
