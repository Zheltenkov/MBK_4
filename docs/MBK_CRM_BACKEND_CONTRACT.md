# Контракт classification API CRM МБК

Зафиксировано 23–24.07.2026 по сообщению backend-разработчика и безопасным
smoke-запросам. Квалификационные endpoint не создают лиды. Первый `lead-intake`
был отклонён до создания лида из-за обязательного `PHONE_DEAL`; backend затем
подтвердил его значение, dedup policy и lifecycle незавершённой анкеты.

## Граница ответственности

- Внутренняя схема `mbk.lead.v1` хранит все ответы диалога и `null` для
  непройденных веток.
- `delivery.crm_contracts` описывает внешний контракт CRM и enum Bitrix.
- Локальная матрица определяет, какие вопросы задать. Финальная
  `first-qualification` является авторитетной backend-квалификацией.
- `lead-intake` по умолчанию заблокирован
  (`MBK_CRM_LEAD_INTAKE_ENABLED=0`) и не имеет автоматических повторов.
- Отложенные частичные лиды дополнительно защищены флагом
  `MBK_CRM_ABANDONED_LEADS_ENABLED=0`.

## Подтверждённые операции

1. `POST /first-qualification` — итоговая квалификация. Не создаёт лид.
2. `POST /realty-qualification` — проверка первого объекта недвижимости. Не
   создаёт лид.
3. `POST /lead-intake` — создаёт реальный лид.

## Фактическое расширение ответа first-qualification

Боевой endpoint возвращает не только опубликованные `vertical`, `category`,
`need_site_consent`, `thanks_url`, но также:

- `matched`;
- `priority`;
- `suitable_categories`;
- `segment`;
- `partner`;
- `offer`;
- `suitable_offers`;
- `need_partner_consent`;
- верхнеуровневый `success`.

Эти поля добавлены в строгую Pydantic-схему. Backend подтвердил:

- `need_site_consent` управляет шагом оффера в боте. Ответ переводится в
  `UF_SITE_AGREE_PARTNERS`;
- `need_partner_consent` предназначен для оператора колл-центра и ботом
  игнорируется.

Smoke с корректной Unicode-передачей московского адреса вернул
`priority = "1-1"`, `segment = "msk_mo"`, `vertical = "realty_pledge"` и
`category = 2217`. `realty-qualification` вернул `is_first_category = true` для
`"Москва"`, `"г Москва"` и полного адреса. Предыдущий результат `segment = "rf"`
оказался дефектом тестовой команды: PowerShell подменил кириллицу символами `?`.
Это не дефект геоклассификации backend.

## Входные поля квалификации: Битрикс-имена

С 31.08.2026 (crm-mbk, коммит 18490d4d «#97878 Новая партнёрка») обе
квалификации читают те же Битрикс-имена полей, что и `lead-intake`. Анкетного
формата (`amount`, `age`, `residence_region`, `cars`…) у них больше нет. Такие
ключи CRM не видит, профиль клиента выходит пустым, ответ приходит с
`category = null`. Так было у всех квалификаций бота с 31.08 по 14.09.2026.

Профиль строит `CrmLeadProfileMapper::toProfile`, правила проверяет
`RuleMatcher`. Условие, не заданное в правиле, не ограничивает. Заданное
условие при пустом поле профиля не выполнено, кроме наборов, где правило
разрешает «Пустое поле».

`first-qualification` получает:

| Поле | Что это | Как читает CRM |
|---|---|---|
| `SUMM` | сумма | число |
| `BIRTHDATE` | дата рождения `ДД-ММ-ГГГГ` | возраст = `Carbon::parse(BIRTHDATE)->age`; без даты с формы бот шлёт 1 января года рождения |
| `UF_CRM_1452153725` | адрес прописки | регион проживания: Москва/МО или РФ |
| `UF_DEBT_SUMM` | долг, строкой | число |
| `UF_CREDIT_HISTORY` | кредитная история | код |
| `UF_CRM_LOAN_OVERDUE_DURATION` | срок просрочки | код |
| `UF_CRM_1460622474` | занятость | код |
| `UF_CRM_1461049862` | доход | профиль предикта ёмкости кампаний |
| `UF_REALTY_CC_4_22` | есть недвижимость | `4697` — есть |
| `UF_CRM_1452154011` | тип объекта | код |
| `CHAT_REALTY_REGION` | регион объекта, текстом | Москва/МО, списки городов, РФ |
| `CHAT_OWNER` | `CLIENT` / `BOTH` | собственник `4673` / `4675`; без `UF_FORM_OF_OWNERSHIP_FLAT` объект считается частным (`4671`) |
| `UF_CRM_RESTRICTION` | ограничения на объект | профиль предикта ёмкости кампаний |
| `UF_HAVE_AUTO` | есть авто | `4695` / `4696` |
| `UF_CAR_PRODUCTION_YEAR_1`, `UF_CREDIT_AUTO_1` | год и кредит авто | условие года и кредита |

`realty-qualification` получает `UF_CRM_1452154011`, `CHAT_REALTY_REGION`,
`CHAT_OWNER` и отвечает `is_first_category`.

Правила бота:

- Запрос квалификации — срез запроса лида: те же поля, посчитанные тем же
  кодом (`delivery/crm_mapping.py`). CRM классифицирует клиента дважды, по
  квалификации и по лиду, и расчёты не должны расходиться. Держат это
  `tests/test_crm_qualification_contract.py` и
  `tests/test_lead_intake_invariant.py`.
- `CHAT_OWNER` передаётся только при подтверждённой частной собственности. Кода
  муниципальной собственности у нас нет, а названный собственник делает объект
  частным. Муниципальный объект не должен открывать залог.
- Отсутствующий ответ передаётся `null`. `category = null` не отменяет лид:
  `lead-intake` вызывается обязательно.
- Для недвижимости передаётся второй объект, если он квалифицирующий, в ключах
  первого, иначе первый.

## Подтверждённые enum

- Недвижимость: квартира `190`, дом/коттедж `191`, таунхаус `192`,
  апартаменты `194`, комната `2265`, коммерческая `3075`.
- Собственник: клиент единолично `4673`, клиент и супруг(а) `4675`.
- Частная собственность: `4671`.
- Авто: есть `4695`, нет `4696`.
- Авто в кредите: да `4699`, нет `4600`.
- Активы: есть `4697`, нет `4698`.
- Кредитная история: нет просрочек `9255`, были `9256`, есть сейчас `9257`,
  готов оформить банкротство `9258`.
- Текущая просрочка: нет `22606`, до месяца `22602`, 1–3 месяца `22603`,
  3–6 месяцев `22604`, более 6 месяцев `22605`.
- Занятость: официально `376`, найм `3082`, бизнес `377`, неофициально `2703`,
  самозанятый `15001`, пенсионер `15002`, не работает `378`.
- Согласие партнёрам: да `23000`, нет `23001`, не требуется `23002`.

Полный переданный `Leads::mapBitrix24` для клиента, паспорта, адресов,
кредитной нагрузки, работы, недвижимости, трёх автомобилей, согласия и аналитики
зафиксирован в `delivery.crm_contracts.LeadIntakeRequest`.

Боевой smoke выявил расхождение с опубликованным обязательным минимумом. Запрос с
`PHONE`, `UF_FROM_SITE_FILLED_OUT`, `RETURN_RESPONSE` и тестовым ФИО получил:

```json
{
  "success": false,
  "data": {
    "PHONE_DEAL": ["The phone deal field is required."]
  }
}
```

Backend подтвердил: `PHONE_DEAL` содержит тот же нормализованный номер, что и
`PHONE`. Контракт валидирует обязательность и равенство обоих полей.

## Idempotency и дубли

- Idempotency key и внешний ID отсутствуют.
- CRM дедуплицирует по телефону в окне 15 минут.
- Повтор в этом окне возвращает `leadID` существующего лида, но полностью
  игнорирует новое тело: дозаполненные данные не обновятся.
- Повтор после 15 минут создаёт второй лид.

Application policy: один lead-intake на session id. Перед POST состояние атомарно
становится `in_flight`; успешный `leadID` сохраняется как `submitted`. Timeout или
обрыв с неизвестным результатом становится `outcome_unknown`; автоматического retry
нет. Восстановленный `in_flight` также переводится в `outcome_unknown`.

Если клиент вернулся после уже созданного частичного лида, текущая сессия не делает
второй POST и отмечает `resumed_after_submission=true`. Дозаполненные сведения нужно
обрабатывать через существующий лид/колл-центр, потому что повторный API-запрос либо
потеряет тело, либо создаст дубль.

## Незавершённая анкета

- Отправлять обязательно, если телефон уже получен.
- Ждать 15 минут без сообщений клиента.
- Таймер сбрасывается каждым новым сообщением.
- Передавать `UF_FROM_SITE_FILLED_OUT=0`.
- Не передавать `UF_SITE_AGREE_PARTNERS` вообще.
- Без телефона lead-intake не вызывается.

Policy реализована в `lead_intake_coordinator.py`; scheduler запускается только при
двух явных флагах:

```text
MBK_CRM_LEAD_INTAKE_ENABLED=1
MBK_CRM_WORKFLOW_ENABLED=1
MBK_CRM_SUBMISSION_MODE=test
MBK_CRM_TEST_PHONE_ALLOWLIST=79991234567
MBK_CRM_ABANDONED_LEADS_ENABLED=1
MBK_CRM_ABANDONED_INACTIVITY_SECONDS=900
MBK_CRM_ABANDONED_SCAN_SECONDS=30
```

## Что ещё требуется для production

1. Подтвердить механизм доступа: bearer token, подпись, IP allowlist или иной.
2. Подтвердить стабильность ошибок `{success, message, data}` и возможные HTTP-коды.
3. Подключить Redis/БД платформы для атомарного session/lead state. Локальные
   обезличенные snapshots диагностические и не восстанавливаются после рестарта.

## Правила безопасного теста lead-intake

- Использовать только ФИО `Тестов Тест Тестович`.
- В локальном test-mode номер также должен входить в
  `MBK_CRM_TEST_PHONE_ALLOWLIST`; сам allowlist не отдаётся frontend.
- При другом имени/номере qualification и lead-intake не вызываются, UI показывает
  только локальный `mbk.lead.v1`.
- Делать один вызов после явного разрешения флагом.
- Не повторять запрос после timeout.
- Передавать одинаковые `PHONE` и `PHONE_DEAL`.
- Сохранить session id, состояние попытки и полученный `leadID`.
