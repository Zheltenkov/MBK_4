# Этап 1: текущая анкета в боте

Дата: 06.11.2026. Первый локальный этап реализован и проверен. Production
не включён; готовность всего сценария сайта и онлоадера не заявляется.

## Результат

Бот может получить текущую анкету через явно подключённый доверенный backend,
использовать нормализованные сведения и не запрашивать уже известные поля.
Доступ привязан к владельцу чат-сессии и подписанной ссылке на конкретное
обращение. Произвольный телефон, form-id или данные браузера доступа не дают.

Реализован настоящий HTTP/session путь: создание с `context_expected=true`,
затем `POST /api/session/{session_id}/context` с capability. До получения анкеты
сессия ожидает данные; после ошибки не запускает обычную анкету вместо неё.
Повтор той же разрешённой привязки не читает источник ещё раз. Другая заявка,
истёкший доступ или попытка перезаписать начавшийся диалог отклоняются.

Вся новая ветка работает без отправок. Даже статус ready не разрешает consent,
создание лида и отложенную отправку. Снятие этого ограничения относится к этапу
онлоадера, после определения одного отправителя и контракта согласия.

## Что изменено

- `customer_context/`: строгие схемы, подписанный доступ, проверка свежести,
  адаптер текущей формы и отдельный необязательный клиент истории CRM.
- `main.py`, `context_attachment.py`: owner cookie, HTTP-границы, идемпотентная
  привязка и корректное удержание session lock при отмене HTTP-клиентом.
- `context_projection.py`, `pii_masking.py`, `core.py`: только допустимые
  структурированные значения передаются модели. Телефон представлен признаком
  наличия; свободные поля анкеты исключены. Маскирование этой ветки обязательно.
- `context_policy.py`, `entry_routing.py`, `lead_intake_coordinator.py`: общий
  запрет отправок, включая прямой coordinator submit и inactivity timer.
- `Dockerfile`: новые runtime-модули добавлены в явный COPY allowlist.

Архитектура, переходы, откат и границы: [ADR-0004](../adr/0004-authorized-current-application-context.md).
Обычные сессии без нового context сохраняют прежний режим.

## Независимые проверки

Работа разделена между исполнителем backend-контракта, исполнителем интеграции,
независимым критиком безопасности/состояний и независимым автором приёмочных
тестов и мутаций. Итоговые проверки используют настоящие классы приложения;
внешние CRM, модель и покупатель заменены только на границах.

Критики обнаружили и проверили исправления:

1. Redirect мог передать bearer другому адресату. Lookup теперь использует
   отдельный no-redirect opener. У самого regression-теста первоначально был
   слабый shim: его тоже исправили. Отрицательный контроль с удалённым guard
   действительно вызывает падения на 301/302/303.
2. Произвольный адрес анкеты проходил регулярное маскирование. Добавлена
   закрытая проекция фактов; raw address/name/phone и binding digest проверяются
   перехватом actual conversation/extraction сообщений при PII flag=false.
3. Раннее удаление raw facts мешало скрыть известный телефон в новой реплике.
   Теперь исходные значения используются локально для маскирования ДО проекции.
4. Прямой full submit обходил проверки вызывающих слоёв. Общий hold проверяется
   внутри coordinator до mapping, изменения статуса и transport.
5. Полный pytest выявил пропущенные COPY в Dockerfile. Allowlist исправлен;
   проверка состава runtime проходит. Это не утверждение о сборке/деплое образа.

Submission-проверки имеют положительный контроль: одинаковая допустимая обычная
заявка вызывает fake intake ровно один раз, а context-сессия — ноль раз.
Проверены полная и отложенная отправка, включая malformed context. Cancellation
тест подтверждает, что работающий executor не теряет lock после отмены клиента.

Результаты source mutations:
`logs/site-context-2026-11-06/guard-mutations-final.json`.
Копия исходников и тестов фиксируется SHA256; мутации исполняются в отдельной
временной папке, runtime checkout не меняется. До pytest-import разрешаются
только loopback-порты, открытые тестовыми fixtures; боевые соединения запрещены.
Эта проверка отличается от прежних LLM-перефразировок `run_mutation_eval.py`.

## Примеры из текущих диалогов

База прочитана в транзакции с проверенным `transaction_read_only=on` и timeout.
Ограничение: последние 7 дней, до 5000 сообщений, 60 последних доступных сессий.
Из базы вышли только счётчики и булевы regex-признаки; тексты, телефоны,
имена, идентификаторы сессий и URL не экспортировались.

В выборке 18 сессий с признаком долгов, 39 с вопросом о телефоне, 46 — о возрасте,
29 — о сумме кредита. Это автоматические признаки, а не разметка ошибок:
например, фраза «нет долгов» тоже может совпасть с поиском долга. Нельзя считать
эти числа конверсией или доказательством лишнего вопроса. Они помогли выбрать
типы синтетических регрессий; реальные реплики в fixtures не переносились.

Запрос, время, hash и флаги сохранены в
`logs/site-context-2026-11-06/bounded-case-query.sql` и
`logs/site-context-2026-11-06/current-dialog-case-flags.json`.

## Готовность трёх задач Михаила

| Задача | Готово локально | Осталось |
|---|---|---|
| Использовать данные сайта | Авторизация, типизированная текущая форма, HTTP/session путь, отдельный lookup, privacy и ошибки | Реальный ownership/source/issuer API МБК, bounded adapter, CAS и интеграция виджета |
| Долговая ветка | Согласованные требования и изолированный native-стенд из предыдущего этапа | Отдельная policy, короткая анкета, входные сигналы, границы долга и приёмка страницы |
| Онлоадер без повторного телефона | Известный контакт доступен серверу, planner использует известные поля; новый context не создаёт второй intake | Один delivery owner, offer/consent event, receipt, reuse существующего обращения и retry/recovery |

По умолчанию service не подключён. Для локального включения недостаточно flag:
нужны явная injection, отключённый CRM intake и mock delivery. Production lookup
не вызывался, лиды на боевые серверы не отправлялись, изменения не поставлялись.

Ближайший этап — детерминированная долговая policy с границами
189999/190000/299999/300000 и сохранением unknown, без повторного телефона при
подтверждённом контакте. Приёмка партнёрской доставки потребует отдельного
подтверждённого контракта; текущая анкета сама по себе его не заменяет.
