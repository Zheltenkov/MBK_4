# Сокращённая долговая анкета — контракт после сверки с серверным кодом

Дата: 02.11.2026. Версия 0.2. Статус: статически проверено по закреплённым
GitLab SHA; production intake и действующие правила БД не проверены.
Подробные доказательства и ссылки: `СВЕРКА_CRM_И_МАТРИЦЫ_МБК_2026-11-02.md`.

## 1. Что теперь подтверждено

First-qualification использует обычный Request и mapper, lead-intake —
MbkFormLeadRequest с prepareForValidation из pinned библиотеки фильтров.
Из перечисленных полей required только PHONE и PHONE_DEAL. Необязательность
поля для валидатора не равна его необязательности для правила БФЛ или кампании.

Правила 371 загружаются из БД. RuleMatcher отвергает неизвестное, если есть
соответствующее ограничение, кроме разрешённого '0' в наборе как «пустое поле».
Product intent debt/restructuring сам по себе не ограничивает выбор вертикали.
За отправкой lead-intake могут следовать асинхронные поставки, включая Soda
для NO_CATEGORY. Внешний referral до подтверждения delivery state заблокирован.

## 2. Поля: кодовая гарантия и оставшийся вопрос

| Поле | Подтверждено по коду | Что остаётся проверить |
|---|---|---|
| SUMM | В intake nullable\|string; mapper qualification оставляет null, normalizer intake после классификации превращает отсутствие в 0 | Допустим ли такой конечный 0 для полного короткого лида/покупателей; не переносить сюда сумму долга |
| BIRTHDATE | Nullable\|string; отсутствие даёт age=null в профиле | Нет ли AGE_MIN/MAX у нужных действующих правил 371; downstream Bitrix/runtime |
| UF_DEBT_SUMM | Nullable\|string, mapper приводит к int; наш клиент сериализует числовую оценку строкой | Активные DEBT_MIN/MAX, BFL_DEBT_SUMM_SETTING; диапазон сначала уточняется |
| UF_CRM_1452153725 | Регион проживания: непустая Москва/МО→msk, прочий текст→rf, пусто→null | Какие правила требуют region; не угадывать регион из отсутствия данных |
| UF_CREDIT_HISTORY | Nullable\|int; напрямую читается в профиль | Действующие CREDIT_HISTORY_IN, разрешение пустого; честная обработка просуженного долга, без подстановки «нет просрочки» |
| UF_CRM_LOAN_OVERDUE_DURATION | Nullable в профиле; ограничение проверяется RuleMatcher | Нужен ли срок каждому активному правилу; молчание не равно no_overdue |
| UF_CRM_1460622474 | Nullable\|int и поле employment в matcher | Наборы EMPLOYMENT_IN из БД; не выдумывать занятость |
| UF_CRM_1461049862 | Nullable\|string на intake; числовой 0 фильтром пропускается и не становится строкой. Текущий mapper его исключает | Тестовые варианты omit/null/строка '0'; не менять нынешнюю политику по одному успешному qualification |
| UF_REALTY_CC_4_22 | Nullable\|int на входе; LeadProfile.hasRealty — bool, отсутствие превращается в false | Можно ли обойтись без этого поля в нужном правиле; внутренняя unknown-семантика не гарантирована всеми слоями |
| Тип/регион/собственник объекта | Поддерживаются существующие поля; неизвестный enum не следует выдумывать | Нужны ли для debt и как отключить залоговую ветку без удаления добровольных фактов |
| Количество объектов / ипотека / желание сохранить | Единого нового маппинга под эти три независимых признака нет | Утверждённые UF/COMMENTS и влияние на классификацию; рубрика предварительной консультации |
| UF_HAVE_AUTO и детали | Nullable на intake, hasCar nullable в LeadProfile | Какие активные правила ограничивают авто; пропуск не заполнять отрицанием |
| Предмет интереса | COMMENTS принимается строкой, но не является фильтром вертикали | Отдельный согласованный product scope / политика CRM, а не подмена LANDING или фактов |
| PHONE / PHONE_DEAL | Required\|string; FilterPhone убирает нецифры и заменяет ведущую 7 на 8; локальная схема требует равенство | Склейка receiver и повторы между источниками; реальные данные для статической проверки не требуются |
| NAME / FULL_NAME | String без required; отсутствие допустимо для входного правила, null не то же, что отсутствие | Приём и доставка без имени в тестовом контуре, требования downstream title |
| UF_FROM_SITE_FILLED_OUT | Нет required-правила в FormRequest; router при empty отправляет в КЦ, qualification сам принудительно ставит 1 | Считать ли короткую анкету полной и каким набором фактов подтверждать это решение |
| UF_SITE_AGREE_PARTNERS | Nullable\|int; явное NO гейтит только правила needSiteConsent и направляет в КЦ | Тексты/порядок согласия и независимое согласие на новый RF; отказ от продукта не переводить в consent=no автоматически |
| LANDING / current page | Виджет сейчас отправляет utm.landing из исторической cookie | Добавить отдельный очищенный context в согласованном контракте; query/ПД не класть в аналитику |
| form-id | Сайт умеет GetDataByFormId, но AiChatWidget не передаёт это боту | Явный безопасный доступ, сопоставление анкеты и дедупликация; сам ID не авторизация |

Примечание по фильтрам: это кодовая интерпретация по composer.lock V1.3,
а не запуск PHP. Пустые значения фильтры не преобразуют; непустые scalars
попадают в строковые фильтры до validation. Поэтому типы JSON нельзя оценивать
по одному rules() без prepareForValidation. Не добавляем лишнюю сериализацию
или новые отрицательные значения ради прохождения этого слоя.

## 3. Проверочные случаи

Файл: `docs/v5/debt_qualification_requests_2026-11-02.json`.
Восемь запросов валидны по нашему Pydantic, не отправлялись в production.
Телефона/ФИО и реальных клиентов нет. Ожидаемые категории остаются null:
без экспортированных правил и тестового ответа их нельзя назначить честно.

| ID | Условия | Что проверяем на согласованном стенде |
|---|---|---|
| Q01 | Долг 189999, Москва, история has_overdue | Исход ниже коммерческого порога, не юридический запрет помощи |
| Q02 | Долг 190000, Москва, известный доход/история | Реальные category/partner/offer и нижняя граница; код партнёра sodatech_190 |
| Q03 | Долг 299999, Москва, история известна | Сопоставление с текущим верхним порогом/правилами, без предположения что max=300000 |
| Q04 | Долг 300000, Москва | Реальное правило, а не автоматическое ожидание категории по старой YAML |
| Q05 | Долг 300000, Тула | Региональное правило и доступность кампании |
| Q06 | Долг 190000, регион неизвестен | Region null в CRM против default-гео в campaign tagger; данных нельзя достраивать |
| Q07 | Долг 190000, история и просрочка неизвестны | Нужен ли ответ для действующего правила; отличить это от отсутствия покупателя |
| Q08 | Qualification с числовым доходом 0 | Только отдельная ветка qualifier. Это не отрицательный runtime-тест intake; его 0/null/omit проверяются отдельно |

Q02 и Q07 теперь различаются явно: у Q02 UF_CREDIT_HISTORY=9257 как заданный
синтетический ответ, у Q07 null; это не автоматический вывод «долг→просрочка».

Поведенческие проверки до любого live-пилота:
- Долг 250 тыс. и «активных кредитов нет»: не выводить debts.total=0.
- Диапазон 150–250 тыс.: уточнить scalar, не выбирать сторону порога.
- Не спрашивали авто/доход/ипотеку: различать unknown/not_asked/declined.
- matched=false vs matched=true/category=null vs capacity/no_offer/error.
- Созданный lead_id при pending Soda, marker после timeout и реальный receipt.
- Отказ от продукта, отказ от передачи партнёрам, отмена заявки — разные сигналы.
- Параллельные вкладки/источники, callback consent, повторное распределение.

## 4. Минимальный остаток вопросов Андрею

1. Экспорт активных правил 371: приоритет, MIN/MAX/наборы, канал, category,
   partner, offer, consent и widget-флаг; значение BFL_DEBT_SUMM_SETTING.
2. Релевантные campaign/tag settings: active/limits, hands_count,
   frozen_days/duplicate_days, допустимость повторной поставки, source scope.
3. Как ограничить маршруты долговым продуктом честно, если client intent
   сейчас не входит в matcher? COMMENTS достаточно оператору, не движку.
4. Как бот узнаёт delivery outcome, Soda pending/assumed_sent/confirmed,
   КЦ и собственную обработку МБК, чтобы безопасно выбирать RF?
5. Подтверждение deployed commit/runtime и downstream receiver: никакой
   гарантии 15-минутной идемпотентности только по комментарию в контроллере.
6. Тестовый приём без SUMM/возраста/авто/имени и разницы omit/null/zero,
   без production-лидов. Тестовый телефон — только staging allowlist владельца.

## 5. Критерии закрытия

Нужны и кодовая сверка, и DB-правила/настройки, и тестовый end-to-end результат.
Qualification не создаёт лид, но обращается к прогнозу ёмкости; прогноз не
резервирует место. Ответ intake содержит только leadID и не подтверждает
партнёрскую доставку или оплату. Никаких новых ключей статуса в API пока нет.
Подтверждение входной optional-схемы уже получено; весь этап 0 ещё не закрыт.
