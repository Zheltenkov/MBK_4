### 1. У БФЛ два разных входных контракта

`crm:lara/routes/api.php:97–103` оставляет рядом `/mbk-form/lead` и `/classification/lead-intake`. Выбор пути должен быть явным, с отдельными схемой запроса и проверкой результата.

Специальная анкета считает **целочисленную сумму долга и месячного платежа**, а не только долг: `(int) total_credit + (int) total_credit_pay`. При сумме <300000 она ставит отсутствие категории, иначе БФЛ Мск/МО либо Регионы. Проверка региона — регулярное выражение по адресу регистрации. Маппинг передаёт собственно долг и месячный платёж разными полями, `SUMM='0'`, `UF_SITE_AGREE_PARTNERS=23000`, `IS_BFL_PRODUCT=true`.

Доказательства: `site:www/app/Http/Controllers/LeadsBflController.php:49–64,79–99`; `site:www/app/Models/LeadsBfl.php:57–60,90–104`.

Обычный классификатор читает долг из `UF_DEBT_SUMM` и регион из `UF_CRM_1452153725`. Диапазоны 190000–299999 / ≥300000 и допустимая история сообщены Андреем; без строк таблицы правил их текущие значения не подтверждены исходниками. `RuleMatcher` позволяет настраивать возраст и сумму, поэтому отсутствие таких ограничений для БФЛ — свойство правил, а не универсальная гарантия движка.

Доказательства: `crm:lara/app/Services/Classification/CrmLeadProfileMapper.php:56–75`; `crm:lara/app/Services/Classification/RuleMatcher.php:14–27`.

**Блокер адаптации:** текущий `delivery/crm_contracts.py:379` запрещает `SUMM=0` (`gt=0`), а `delivery/crm.py` работает с classification endpoint. Независимый локальный вызов `LeadIntakeRequest.model_validate` подтвердил ошибку `greater_than` для нуля. У DTO нет aliases `IS_BFL_PRODUCT`, `LEAD_CHANNEL`, `ADDRESS_PROVINCE`; согласие есть. Нельзя получить специальный БФЛ-путь простой заменой URL или ослаблением кредитного DTO: требуется отдельный согласованный контракт.

### 2. IS_BFL_PRODUCT не является безопасным переключателем продукта

В legacy-приёме категория БФЛ направляется в партнёрку при **согласии YES ИЛИ флаге IS_BFL_PRODUCT**. При отсутствии обоих ставится ветка БФЛ КЦ. Для специальной анкеты сайт сам проставляет YES, считая отправку формы согласием. Это предположение конкретного UX, а не разрешение подменять отказ клиента флагом в чате.

Флаг не отменяет более раннюю ветку недвижимости: переданная категория 1 проверяется прежде БФЛ. Поэтому долговой адаптер должен валидировать и категорию, и продуктовый scope, и подтверждённое согласие.

Доказательства: `crm:lara/app/Http/Controllers/LeadController.php:434–485`; `site:www/app/Models/LeadsBfl.php:100–104`. У обычной анкеты есть собственный расчёт YES/NO/NOT_REQUIRED и особый случай этого же флага: `site:www/app/Models/Leads.php:298–309,339–349`.

### 3. Отсутствие категории ещё не доказывает отсутствие отправки

`IS_BFL_PRODUCT + NO_CATEGORY` пропускает обычный `processPartners()`, **но ниже остаётся постановка `SendLeadSodaTechDirect`**, если обычная партнёрка не сообщила об отправке. Это относится и к другим веткам, где обычной отправки не было. Утверждение «190–299 тыс. в специальной анкете точно потеряны» неверно без исполнения фоновой задачи.

Свежий Direct проверяет `NO_CATEGORY/БФЛ CPA`, **UF_DEBT_SUMM + UF_TOTAL_DEBT_OTHER**, минимум 190000 включительно и верхнюю границу из БД исключительно. Это **третья формула**, отличная от долга + месячного платежа сайта. Максимум получается из `BFL_DEBT_SUMM_SETTING`; его реальное значение 300000 исходниками не доказано. Base проверяет наличие лида/subData, прежнюю отправку этому потоку по ID лида и повторно eligibility. Проверок кредитной истории, региона, возраста, согласия, frozen/duplicate_days телефона в Direct/Base нет.

Доказательства: `crm:lara/app/Http/Controllers/LeadController.php:477–485,573–586`; `crm:lara/app/Jobs/SendLeadSodaTechDirect.php:39–54`; `crm:lara/app/Jobs/SendLeadSodaTechBase.php:70–94,229–235`; имена двух долговых полей — `crm:lara/app/Models/BUtsCrmLead.php:640,687`.

Отсутствие проверки `UF_SITE_AGREE_PARTNERS` у CPA здесь **явное существующее продуктовое правило**: `crm:lara/app/Services/Classification/LeadIntakeService.php:128–131` прямо пишет, что согласие шага БФЛ к CPA не относится. Нельзя выдавать отказ от БФЛ-партнёров за глобальную отмену CPA. Обычный classification Router режет только явное NO и только кандидата с `needSiteConsent`; отсутствие поля/NOT_REQUIRED не блокирует, а при отсутствии ёмкости БФЛ может идти ниже по матрице. Для debt-scope нужен собственный согласованный запрет выхода в кредит/залог, которого этот маршрут сам не гарантирует.

Доказательства: `crm:lara/app/Services/Classification/LeadIntakeRouter.php:58–84,97–119`. Legacy `MbkFormPartners` дополнительно обходит проверку порога долга и согласия при `IS_BFL_PRODUCT`; проверка истории также учитывает этот флаг: `crm:lara/app/Services/MbkFormPartners.php:254–265,298–314,361–375`.

**Особенность доказательства доставки:** Base при HTTP 2xx ставит `deliveredToSoda=true`; при `ConnectionException`, включая сетевой timeout, делает то же самое и помечает лид отправленным. Timeout установлен в 5 секунд. Поэтому у Direct даже `UF_SHIPPED_*`/имя потока не доказывают получение HTTP 2xx: итог в таком случае — **доставка неизвестна**. Не-2xx вызывает исключение для очереди (до 4 попыток, backoff 60/300/600 секунд). Дедупликация перед отправкой — проверка записи по lead ID, не атомарная телефонная блокировка: конкурентные задачи и повтор после сбоя записи маркера требуют отдельных тестов.

Доказательства: `crm:lara/app/Jobs/SendLeadSodaTechBase.php:36,48–49,152–180,189–206,229–235,262–265`. Это фиксирует существующую семантику; поведение заказчика в данном аудите не менялось.

Повтор, склеенный приёмником (`created=false`), возвращает существующий `leadID` до отправок/уведомлений. При отсутствии флага код считает лид новым. Нужна совместимая версия приёмника, а не только Laravel.

Доказательство: `crm:lara/app/Http/Controllers/LeadController.php:554–561`.

### 4. Регион для правил и для доставки может разойтись

Классификация берёт регистрацию; нормализатор перед приёмом разбирает **фактический адрес** через `AddressParser::parse` и накладывает результат поверх входных полей. По сообщению Андрея партнёрка использует `ADDRESS_PROVINCE`. Текущий DTO бота поля не имеет.

Доказательства: `crm:lara/app/Services/Classification/CrmLeadProfileMapper.php:62–65`; `crm:lara/app/Services/Classification/LeadFieldsNormalizer.php:90–91`; `delivery/crm_mapping.py:455–459`.

Свежий `AddressParser` возвращает `ADDRESS_PROVINCE` **текстовым названием региона**, по возможности каноническим из БД `b_sale_location/b_sale_loc_name` (`ru`), не числовым enum/ID. Поддерживает DaData, `Регион - Город`, `Регион, Город`, свободный текст. В формате Denis неизвестный регион сохраняется исходной строкой; неразобранный свободный адрес также целиком попадает в `ADDRESS_PROVINCE` для ручного разбора. Поэтому наличие поля ещё не означает валидного региона кампании.

В обоих intake-путях `array_merge` накладывает результат парсера **фактического адреса поверх** явно переданного `ADDRESS_PROVINCE`. Если парсер вернул province, он перезаписан; если вернул только другие поля, входной province сохранится. Пустой фактический адрес вообще не запускает парсер. В legacy разбор выполняется после первичного определения ветки, но до `processPartners`; в classification — после classify/route, до сохранения и afterIntake. `MbkFormPartners::checkRegionOfLiving` читает только `ADDRESS_PROVINCE` и regex Москвы, без fallback на регистрацию. Возможна комбинация «категория БФЛ Мск по регистрации, фактический регион другой, московский BFL-флаг снят». Требуется согласовать смысл двух регионов, а не просто добавить alias.

Доказательства: `crm:lara/app/Services/AddressParser.php:33–82,196–205,370–398`; `crm:lara/app/Http/Controllers/LeadController.php:532–535,573–582`; `crm:lara/app/Http/Controllers/Classification/LeadIntakeController.php:35–40,55–56`; `crm:lara/app/Services/MbkFormPartners.php:343–358`.

### 5. Виджет — конкретный канал, а не любое окно чата

Свежий mapper определяет канал только сравнением `LEAD_CHANNEL` с `LEAD_CHANNEL_DENIS_WIDGET`, литерал `denis_widget` подтверждён свежим `crm:lara/app/Services/Bitrix24Api.php:16–17`. UTM не участвуют. Matcher выбирает правила yes/any для виджета, no/any для остальных.

Доказательства: `crm:lara/app/Services/Classification/CrmLeadProfileMapper.php:79–88`; `crm:lara/app/Services/Classification/RuleMatcher.php:43–54`.

Андрей разделил допустимую историю обычного канала и виджета. Нельзя назначать AI-чату канал Дениса автоматически. Сейчас `_derived_credit_history` в `delivery/crm_mapping.py:164–187` всегда возвращает словарь обычной анкеты, в том числе `ready_bankruptcy` при неизвестной просрочке превращается в «нет просрочек». Для нового debt-сценария это требует отдельной согласованной политики, общей для qualification и intake. Отсутствие действующего кредита также не означает отсутствие долга.

### 6. crm-lookup — ограниченная справка по уже известному телефону

- Маршрут защищён bearer middleware; общий endpoint-лимит 100/сутки, ответ 429 `rate_limit_exceeded`. Не ставить автоповтор при 429 и запрос на каждый ход диалога. Точное время сброса в приложении здесь не проверялось.
- FormRequest применяет телефонный фильтр и проверяет строку длины 11; 422 `invalid_phone`. Свежий FilterPhone удаляет нецифровые знаки и заменяет начальную 7 на 8. Проверки, что результат начинается именно с 8, нет: произвольная 11-значная строка другого префикса проходит эту валидацию. Клиенту нужна собственная проверка выбранного телефонного контракта.
- Поиск лида использует точное равенство индексированного телефонного поля. Если лидов нет, немедленно возвращается `{"leads":[]}` без пустого фильтра контактов/сделок.
- Справка включает сделки найденных лидов и их контактов. При общем контакте могут попасть сделки, привязанные к другому лиду: это история контакта, а не только исходной заявки. Сделки дедуплицируются по ID.
- Дерево допускает `leads[].deals` для сделок без контакта; нельзя ограничивать парсер только `leads[].contacts[].deals`. У записи `bitrix_id` — целое ID, у поля — строковый код. `fields` — список объектов `{name, bitrix_id, type, value}`, не словарь по русскому названию; `value` не гарантированно строка. У контакта полей нет. Отсутствующее поле не означает ноль/отказ/false.
- Ошибка CRM даёт 502 `bitrix_error`. Старые лиды 2016–2019 и записи без найденного лида могут отсутствовать по сообщению Андрея: пустой результат не доказывает нового клиента. API не получает телефон по form-id.

Доказательства: `crm:lara/routes/api.php:83–84`; `crm:lara/app/Providers/RouteServiceProvider.php:69–81`; `crm:lara/app/Http/Requests/CrmLookupRequest.php:28–60`; `crm:lara/app/Http/Controllers/Api/CrmLookupController.php:22–39`; `crm:lara/app/Services/CrmLookup/CrmLookupService.php:25–66`; `crm:lara/app/Services/CrmLookup/CrmLookupTree.php:40–56,64–76,90–120`.

Свежий middleware отвергает пустой ожидаемый токен и использует `hash_equals` с bearer, возвращая 401; lookup-token не является пользовательской авторизацией на конкретный телефон. Свежий FilterPhone — `crm:lara/app/Http/Filters/FilterPhone.php:7–14`; middleware — `crm:lara/app/Http/Middleware/AuthApiToken.php:20–36`.

Политика полей теперь проверена: штатные поля — allowlist; строковые динамические UF — отдельный allowlist; остальные динамические UF допускаются по `safe_types` с исключением `hidden`. **Это не закрытая allowlist всех полей:** новое числовое/дата/enum UF включается автоматически, если не попало в hidden. Телефон, ФИО, TITLE, COMMENTS и адресная строка в штатном списке отсутствуют, но province/region и одобренные свободные строки (включая URL) разрешены. Поэтому «без ПДн» не является универсальной гарантией содержимого при развитии схемы/заполнении разрешённых полей.

Декодер сохраняет 0/false для числовых/boolean типов, убирает пустое enum/ссылку, отдаёт enum/status текстом, money объектом `{amount, currency}`, дату без времени, массив — массивом непустых декодированных значений. `type='list'` может сопровождаться скалярной строкой: это тип поля, а не гарантия JSON-массива.

Доказательства: `crm:lara/app/Services/CrmLookup/CrmFieldPolicy.php:18–28,41–52`; `crm:lara/config/crm_lookup.php:24,43–71,75–109`; `crm:lara/app/Services/CrmLookup/CrmValueDecoder.php:11–24,43–78`. Backend-клиент должен фильтровать данные перед передачей в LLM, связывать номер с текущим пользователем и хранить токен только на сервере. Для локального стенда нужен синтетический lookup stub, без боевого токена и реальных номеров.

## Что требуется перед сквозными прогонами

### Уточнение boot и зависимостей Битрикса

В проверенных `bootstrap/app.php`, `public/index.php`, application providers и global/API middleware **немедленной загрузки Bitrix core или обязательного запроса к Bitrix-БД до обработки маршрута не найдено**. Providers регистрируют lazy singleton-closures; AppServiceProvider::boot пустой. `RouteServiceProvider.php:30–36` регистрирует API с префиксом `/lara/api`. Поэтому ошибка `artisan package:discover` сама по себе не доказывает отсутствие Bitrix core.

Конкретная отдельная ловушка boot: `crm:lara/config/app.php:168` безусловно регистрирует `Barryvdh\LaravelIdeHelper\IdeHelperServiceProvider`, хотя пакет в `composer.json:27–28` находится в require-dev. При установке `--no-dev` это кандидат на class-not-found уже при boot; нужно проверять реальный vendor/первую ошибку, а не заменять Bitrix заглушками. Composer вызывает package:discover в post-autoload-dump (`composer.json:67–69`). Эти выводы статические: собственный boot в данной проверке не запускался.

`BitrixAuth` находится в **web-группе маршрутов** (`crm:lara/routes/web.php:27–30`), а не в global/API stack (`crm:lara/app/Http/Kernel.php:17–42`). На соответствующем запросе middleware требует точный относительный путь **`$_SERVER['DOCUMENT_ROOT']/bitrix/.settings.php`** (`crm:lara/app/Http/Middleware/BitrixAuth.php:30–33`). Laravel front controller отдельно расположен в `lara/public/index.php` и требует `lara/vendor/autoload.php` / `lara/bootstrap/app.php`. Следовательно document root для web-Bitrix middleware должен указывать на родителя каталога bitrix, а не автоматически на `lara/public`; абсолютный production-путь и nginx-правило сопоставления из сохранённых файлов здесь не установлены. В снимке отсутствуют `bitrix/.settings.php`, `bitrix/modules/main/include/prolog_before.php` и собственный `lara/vendor/autoload.php`; это отсутствие в snapshot, а не утверждение об отсутствии в отдельном runtime-каталоге агента.

При **classification-запросе** `RuleRepository` читает Eloquent, явно без bootstrap Битрикса: нужны `b_iblock_element`, `b_iblock_property`, `b_iblock_property_enum`, `b_iblock_element_prop_s371`, `b_iblock_element_prop_m371` и данные правил 371 (`crm:lara/app/Services/Classification/RuleRepository.php:15–36,59–86`; имена таблиц — соответствующие модели). AddressParser дополнительно требует справочники `b_sale_location`, `b_sale_loc_name`, `b_sale_loc_type` при поиске региона. Lookup вызывает REST только при выполнении своего service, а не при boot (`crm:lara/app/Services/CrmLookup/CrmRestReader.php:13–16`). Наличие этих таблиц в запущенной БД здесь не проверялось; Laravel-миграции изменяют уже существующие Bitrix-таблицы, а не подтверждают полный рецепт установки Bitrix с пустой БД.

## Дополнение после native runtime — 06.11.2026

Позднее выполнен отдельный положительный сценарий на настоящем официально установленном локальном Битриксе: сайт7 → реальный BitrixID1 → исходный SendLeadMicroservice → нативная партнёрка/localLead1/campaign950 → исходный LeadSend → локальный mock-покупатель HTTP200. В новой пустой схеме строки lead/queue/sent/history/usage/charge созданы runtime, а не фикстурами. Итог: sent1/history1/usage1, списание10/остаток90, очереди и failed0; native Get/ORM подтвердили ID1/ORIGIN и shipped/time/реальный enum15. Полный evidence index и ограничения: `dev/mbk-local/partner-native-result.md`.

Прогон потребовал **одного явного ручного восстановления post-Add отправки**: локальный adapter сначала отверг nullable месячный платёж, затем после настоящего Add ошибся при readback UTM. После исправления только adapter чтение и replay created=false привязали сайт к существующему ID1; исходный CRM при created=false пропускает отправку. Через настоящий Dispatcher поставлен ровно один исходный sender с проверками identity/auth/пустых очередей и durable marker. Это подтверждает настоящие локальные создание и доставку с recovery, но не чистую автоматическую E2E-цепочку. Старые/ошибочные задания и исторические ответы сохранены.

Предыдущий раздел T01–T15 остаётся планом полного регресса: один положительный native delivery не подтверждает все границы/дубли/лимиты/lookup/таймауты. Настройки кампании — user_fixture, локальный API использует настоящие native API с Basic через узкий adapter, а не production receiver/REST OAuth. Поле double_count партнёрской схемы явно inferred_from_native_code, точная production DDL/phone-race не заявляются. Терминальная квитанция принадлежит локальному mock, не реальной компании.
