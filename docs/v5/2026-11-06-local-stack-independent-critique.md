# Независимая проверка локального контура МБК

Последующее продолжение с synthetic-write/отдельным protocol receiver проверено
в [отдельном отчёте](2026-11-06-synthetic-write-critique.md). Этот документ
сохраняет историю первоначальной сборки и проверок.

Дата: 06.11.2026. Исполнитель: independent_critic; роль — проверка, не сборка.
Первый проход: compose/capture/probe, контракт Андрея, выборка исходников от
06.11 и read-only Docker inspect. Браузер, production API и реальные телефоны
не использовались. Приложения и настройки не изменялись.

## Находки

### P1 — probe может показать успешную изоляцию при недоступном контрольном узле

Доказательство: `dev/mbk-local/probe.py:37–49`: любой OSError соединения с одним
адресом TCP/443 превращается в external_tcp_blocked=true. Встроенного результата
положительного host-control нет; default 1.1.1.1 может быть недоступен и на хосте.
README правильно требует отдельный контроль, но команда запуска его не навязывает.

Условие закрытия: фиксировать успешное соединение с тем же адресом/портом на
хосте непосредственно перед отрицательной проверкой; без контроля результат
считать inconclusive. Проверять каждый сервис после добавления сети. Тест
единственного IPv4 TCP-направления не доказывает отсутствие DNS/UDP/IPv6,
доступа к host/proxy, обхода через dual-homed gateway или дополнительных сетей.
Для этих рисков нужны проверка топологии и направлений, а не формулировка
«полностью запрещён весь egress». Текущий capture сам исходящих вызовов не делает.

### P1 — штатные compose заказчика не являются безопасным локальным override

Доказательство: snapshots project-1/docker-compose.yml:129–131 и
project-3/docker-compose.yml:71–75 используют external networks; оба
docker-compose-test-local.yml добавляют host.docker.internal:host-gateway.
Mailhog в партнёрке перехватывает только настроенный SMTP, не HTTP/SDK/очереди.

Условие закрытия: новый standalone compose после разрешения переменных должен
иметь внутреннюю сеть для всех приложений, БД и workers; без host network,
external/default networks, host-gateway, host sockets и исходящих proxy.
Будущий входной gateway не должен быть универсальным HTTP CONNECT/forward proxy
и не должен давать приложениям транзит наружу. Публикация UI только на loopback.
Проверять эффективную конфигурацию и реальные сети каждого контейнера.

### P1 — браузер на хосте находится вне Docker internal

Это риск будущего UI-прогона, не наблюдавшаяся отправка. Проверенный compose
изолирует контейнер, но Windows-браузер загружает HTML/JS и выполняет запросы
на хосте. В проверенной sources-выборке нет полного frontend dependency graph;
отсутствие production form action/fetch/analytics/CDN/redirect не доказано.

Условие закрытия до первого открытия локального сайта: проверить frontend
endpoints, ссылки форм, сторонние scripts/пиксели/websocket/service workers;
использовать локальные assets и dedicated browser context без старого состояния,
при возможности блокировать запросы вне локального allowlist. Не считать
container probe доказательством изоляции браузера. Даже синтетические заявки
не должны попадать в production, включая аналитику и внешние формы.

### P1 — подмена согласия через IS_BFL_PRODUCT и непрослеженный Direct fallback

Доказательство: project-1/www/app/Models/LeadsBfl.php:103–104 всегда задаёт YES и
IS_BFL_PRODUCT. project-2/lara/app/Http/Controllers/LeadController.php:455–460
пропускает в партнёрский путь при YES **или** IS_BFL_PRODUCT. Ни интерес клиента
к долговому продукту, ни наличие этого флага сами по себе не являются согласием.

Дополнительно LeadController.php:477–484 пропускает обычный partner processing
для IS_BFL_PRODUCT+NO_CATEGORY, но строки585–586 всё равно ставят
SendLeadSodaTechDirect, если успешный partner processing не произошёл.
Комментарий project-1/www/app/Models/Leads.php:343–345 «не к партнёрам» не
доказывает отсутствия последующей Direct-отправки. Сам dispatch ещё не доказывает
доставку: фильтры job в этой выборке не прослежены.

Условие закрытия: сохранять явное состояние consent (yes/no/not_asked), источник
и версию текста; не подставлять YES и не переносить флаг в чат без протокола.
Нужно разделять согласие на конкретную партнёрскую передачу, условия CPA и общий
отказ клиента. Свежий Classification/LeadIntakeService.php:128–131 прямо говорит,
что для CPA поле «Согласие с сайта» не применяется; поэтому любой Direct при
UF_SITE_AGREE_PARTNERS=NO нельзя автоматически объявлять нарушением текущего
контракта. Интерфейс не должен обещать общий запрет, если код его не обеспечивает.
Синтетические consent cases должны пройти всю цепочку с workers, включая Direct,
и подтвердить выбранную продуктовую семантику. До завершения проверки интеграции
только локальные, очереди не боевые.

### P1 — основной CRM-контроллер журналирует полные поля клиента

Доказательство: project-2/lara/app/Http/Controllers/LeadController.php:392 пишет
request->all(), строка538 — весь requestFields; также строки92/260 пишут
partner payload. Capture не сохраняет raw body, однако это не очищает журналы
CRM, сайта, nginx, workers и исключений. CrmLookupController.php:32 пишет
текст исключения; его отсутствие персональных данных не подтверждено.

Условие закрытия для локальных прогонов: исключительно искусственные данные,
пустые новые log/queue volumes, никаких production .env/секретов/lookup bearer,
никаких неоценённых SQL-дампов с клиентами. Секреты из архивов не печатать и не
переносить в отчёт. Перед использованием реальных данных нужен отдельный
контроль redaction во всей цепочке, не только capture.

### P1 — повторная обработка и несколько владельцев отправки ещё не закрыты

Доказательство: LeadController.php:554–561 прекращает постобработку только если
receiver вернул created=false. Отсутствующий created считается true — совместимость
со старым receiver. Это не доказывает защиту при параллельном site/bot submit,
таймауте после записи, фоновой незавершённой анкете и повторной доставке очереди.
Контракт онлоадера/form-id и единственного владельца отправки пока не определён.
frozen_days/duplicate_days/hands_count/delay_minutes даны именами без значений.

Условие закрытия: явно выбрать владельца создания лида, версионировать контракт
created/idempotency key, проверить concurrent submit и retry после unknown outcome.
Различать технический дубль одной операции и разрешённую бизнес-рассылку нескольким
партнёрам. Не фиксировать «один получатель» либо 30 дней без конфигурации.
Shipped из Битрикса не считать receipt покупателя; отсутствие постбека не считать
разрешением отправить второму покупателю. Выгрузка sent не требуется для первого
этапа: недоступный buyer outcome остаётся unknown, автоматический fallback выключен.
Дополнительное доказательство из полного свежего snapshot:
SendLeadSodaTechBase.php:174–179 при ConnectionException помечает отправку через
markAsSentSafely; следовательно shipped не гарантирует даже наблюдавшийся HTTP2xx.
Для такого пути результат — unknown, не доказанная доставка и не безопасный retry.

### P1 — запущенный capture и тесты бота не доказывают готовность трёх приложений

Доказательство: compose содержит только capture и probe; свежая sources-выборка
содержит26 файлов. Полная схема Битрикса, актуальность правил, тестовые seed,
версии приватных образов и миграции пустой БД пока не проверены этим аудитом.

Условие закрытия: отдельно фиксировать boot каждого настоящего приложения, БД и
workers; запрос из сайта должен пройти реальную локальную обработку CRM и
партнёрки, закончиться ожидаемыми локальными изменениями/событиями. HTTP200
capture не является CRM leadID, квалификацией, созданием лида или принятием клиента.
Если нужен stub, описывать точную подменённую границу и не называть прогон full stack.

### P2 — capture ограничен как источник доказательств и обработки HTTP

Доказательство: capture.py:44–61 допускает отсутствие Content-Length как0,
не проверяет фактическую длину после read и не задаёт socket timeout. Строка65
использует ThreadingHTTPServer; события ограничены1000 и перезаписываются в RAM.
В событии нет correlation ID, времени, вызывающего сервиса или результата бизнеса.
Хеш одинакового низкоэнтропийного тела позволяет сопоставление и не является
универсальным обезличиванием реального телефона.

Условие: достаточно для текущего одного synthetic network marker. Для бизнес-
тестов нужны точные локальные адаптеры/ассерты, контролируемые ошибки/задержки,
bounded requests и воспроизводимое сохранение безопасных доказательств;
пропущенные события после переполнения/рестарта не интерпретировать как «не отправлял».

## Условия повторной проверки перед стартом приложений

Нужны новый compose и перечень локальных интеграций/seed. Критик проверяет
эффективную топологию, mounts, environment **без вывода значений секретов**,
автозапуск workers/cron, свежесть БД/очередей, замены всех отправителей и ingress.
До этого разрешён только текущий синтетический perimeter.

Прочитаны новые apps.compose.yaml, Dockerfile.php, start-app.sh, router.php,
mysql-init.sql и prepare_snapshot.py. Сервисы не запускались. У исходной
sources-выборки все26 SHA256 совпали с manifest.json.

команда запуска только проверяет autoload/index и стартует php built-in server.
Нет customer entrypoint, artisan migration, cron, supervisor или worker.
Публикаций портов/host socket/extra_hosts в draft нет. router.php ограничивает
статические файлы public-root. Это положительный статический результат.

**Pre-start verdict остаётся pending:** локальные env ещё не созданы/не проверены,
итоговый merge compose не валидирован. Требуется проверить имена/назначение
environment без печати значений. Именованный local-database сохраняется между
прогонами: mysql-init.sql работает только на новой БД; происхождение уже
существующего volume надо подтвердить, нельзя считать его пустым автоматически.

Дополнительные замечания переданы исполнителю:

- P2 воспроизводимость: --revision проверяется на формат, но сам по себе не

- Extractor теперь исключает .env*, *.env, *.env.*; абсолютное утверждение

## Допуск искусственных лидов и workers

**Синтетические бизнес-прогоны допустимы после проверки технической изоляции
исполнителем local_stack. Неизвестные consent/Direct/dedup outcomes — цель тестов,
их не требуется заранее объявлять правильными.** Отдельное согласование каждого
искусственного лида/worker не нужно. Условия выполнения:

1. Только искусственные личности/телефоны/анкеты и свежая локальная БД с
   проверенными fixtures. Новый volume и очереди не содержат production records,
   delayed jobs или старые боевые задания. Сохраняется происхождение seed.
2. Никаких production .env, bearer lookup, cookies, SDK credentials или host UI.
   Генерируемые local APP_KEY/DB passwords допустимы. Сохранённые в исходниках
   production defaults не дают права подключать внешний маршрут или proxy.
3. Для каждой конечной интеграции — локальный совместимый mock/receiver:
   CRM/Bitrix, SodaTech/прочие партнёры, SMTP, callbacks и используемые SDK.
   Учитываются Direct fallback, retry и delayed jobs. Mailhog не заменяет HTTP
   mocks. Неподменяемый endpoint должен приводить к локальному ошибочному исходу;
   ради прохождения теста нельзя открывать production egress.
4. До первого fixture local_stack проверяет каждый runtime: приложение, worker,
   scheduler (если нужен), DB/mocks и test driver. Inspect подтверждает только
   internal network, отсутствие extra host/proxy/socket/дополнительных сетей.
   Runtime probe подтверждает доступность локального receiver и недоступность
   внешнего контрольного адреса при положительном контроле с хоста. Проверяются
   host gateway/proxy и фактический transport используемого runtime; результат
   фиксируется с контейнером/временем. Один probe в соседнем контейнере недостаточен.
5. Worker запускается ограниченно на нужной локальной очереди, с конечным временем
   и контролируемыми retry. Если это exec в уже проверенном PHP-контейнере, он
   наследует его сети/env/mounts; запуск отдельного worker требует такой же проверки.
   Не включать все cron/периодические кампании целиком ради одного сценария.
6. Для теста фиксируются synthetic case ID, исходные данные, ожидаемая семантика
   согласия/дубля, события локальных получателей и результат очереди. Ошибка,
   таймаут, обнаруженная отправка без ожидаемого согласия или дубль — допустимый
   результат проверки, требующий исправления перед релизом. Не подменять его pass.

Повторно прочитан эффективный compose после добавления read-only vendor mounts:
apps.compose.yaml SHA256 CD00E5BE5697F0084783ED0A12C6C8BB3E18FEE91D025CDD847932C9CFFDC348.
Нового пути утечки в этом изменении не обнаружено: приложения по-прежнему только
isolated, без ports/extra_hosts, исходники и vendor read-only. Уже запущенный
database независимо inspect-проверен: только internal isolated, port bindings
пусты, новый lab volume имеет ожидаемые provenance labels. Это не самостоятельная
проверка egress будущих PHP/workers: её выполняет local_stack до fixtures.

**Текущий вывод:** конкретного блокирующего утечку дефекта в reviewed compose
не найдено. После перечисленных egress/mock/fixture checks искусственные лиды

## Третий проход: runner с обязательным положительным контролем

Прочитаны verify_runtime.py, runtime-probe.php, новый probe.py, актуальные compose
и runtime-isolation.json. Runner не запускался повторно критиком: исключены гонка
с работой local_stack и дополнительные обращения из контейнеров.

**Первоначальный P1 одиночного отрицательного probe закрыт для штатного пути
verify_runtime.py.** Он валидирует public IP, требует успешное соединение хоста
с тем же IP/443 и только потом передаёт новый control_id perimeter/PHP-проверкам.
Ненулевой exit code, ошибка JSON и несовпадение control_id приводят к ошибке.
Старый probe без target/control_id теперь завершается ошибкой, а не green.
Runtime-probe.php выполняется в настоящем PHP-контейнере, проверяет локальный POST,
публичный адрес и несколько gateway/host направлений. Это существенное усиление.

Предоставленный артефакт `logs/local-stack-2026-11-06/runtime-isolation.json`
от 2026-11-06T15:29:59 UTC содержит согласованный control_id, положительный
host-control 77.88.55.242:443, perimeter и **только partners runtime**. Его нельзя
использовать как подтверждение site/CRM или будущих отдельных workers. Их прогон
выполняется по мере готовности, что не мешает уже допустимым synthetic-тестам
проверенных компонентов.

Остались ограниченные риски интерпретации результата; новых блокирующих путей
утечки в рассмотренной конфигурации не обнаружено:

- P2 — verify_runtime.py:80–81 перезаписывает общий JSON только при успехе.
  Неуспешный повтор оставит предыдущий успешный файл. При использовании артефакта
  как gate сверять успешный exit code текущего запуска, его control_id/время и
  требуемый список runtimes. Улучшение: отдельный результат для каждого run,
  либо явный failed/current status, без потери предыдущих свидетельств.
- P2 — результат не фиксирует container ID, StartedAt, image ID и хеш compose.
  После recreate результат может относиться к прошлому контейнеру. До fixtures
  повторять проверку после изменений/recreate либо привязывать отчёт к этим
  идентификаторам. Команда exec через compose также может выбрать другой контейнер
  при одновременном recreate, поэтому во время проверки конфигурацию не менять.
- P2 — runner inspect проверяет internal/network membership, port bindings,
  privileged и read-only rootfs; он не является полным валидатором mounts,
  extra_hosts, capabilities, user и proxy environment. Эти свойства проверены
  отдельным review compose, их изменение требует повторного review. Ошибочный
  socket/Docker API mount не должен считаться безопасным только из-за green runner.
- Внешний контроль пока IPv4 TCP/443; отрицательные host/gateway попытки без
  собственного positive control доказывают недоступность конкретных служб,
  не отсутствие всех возможных host-сервисов. Формулировка результата остаётся
  ограниченной проверенными направлениями и текущей топологией.

Новый empty tmpfs `/app/database/csv` наследуется всеми PHP-сервисами и скрывает
непроверенные CSV в image/source mount. Это снижает риск автоматической загрузки
такого набора при старте. Это не универсальный фильтр данных: другие fixtures,
пути импорта и содержимое SQL по-прежнему проверяются перед использованием.

## P1: is_crm_sent в site job не является подтверждением приёма CRM

Дополнительно независимо прочитан свежий
project-1/www/app/Jobs/ProcessSendLeadBfl.php:35–48. После HTTP POST worker
сразу присваивает is_crm_sent=true. Затем проверяет HTTP failure или отсутствие
result.leadID; при таком исходе сохраняет true вместе с crm_response и помечает
job failed. Следовательно флаг не доказывает успешное создание/приём CRM.
Это подтверждённая семантика кода; название флага само по себе не устанавливает
его продуктовый контракт. ConnectionException до присвоения — отдельный исход.

В артефакте без запущенного worker ожидаются очередь с локальным адресом CRM,
is_crm_sent=false и отсутствие CRM leadID. Наличие job/флага true нельзя выдавать
за сквозную доставку. Для worker-тестов раздельно фиксировать attempted/HTTP
response/leadID/failed-or-unknown; таймаут или пустой ID не дают права слепо
создавать вторую заявку. crm_response сохраняет тело ответа до10000 символов:
для synthetic это допустимо, реальный ответ потребует контроля редактирования ПД.

для фиксации уже найденного ограничения.

  текущих container IDs, control_id и aggregate config hash a3974b2b… .

  публичный CMS `/bankruptcy`404 без контентного seed. Критик не считает это

- site-bfl-smoke.json:4сессии/12POST прошли с cookies и настоящим CSRF.

  SQLSTATE42S02; тело HTTP/SQL/контактные данные не раскрываются.

**Подтверждённый достигнутый путь:** настоящий сайт → сохранение синтетического
BFL-лида → локальная очередь → один настоящий job → legacy endpoint локальной
CRM → ошибка отсутствующей таблицы Битрикса. Это воспроизведённый integration
blocker reader-fixture, а не успешное создание CRM-лида. Для продолжения нужны
обоснованный write-receiver/минимальные Bitrix fixtures либо явно обозначенный
mock этой границы; выдавать выдуманный CRM leadID ради зелёного результата нельзя.

status=passed у post-worker **DB verifier** означает совпадение с ожидаемым
состоянием после ошибки, а не успешную доставку. Worker CLI log печатает FAIL,
затем DONE: ручной this->fail() и возврат из handle объясняют, почему DONE/exit0
также не доказывают приём CRM. Найденная семантика is_crm_sent=true при HTTP500
подтвердилась реальным локальным экспериментом, не только чтением кода.

**Окончательный вердикт критика:** изолированные настоящие приложения и
ограниченные synthetic-прогоны работают; нового конкретного пути утечки в
проверенной конфигурации не обнаружено. Допуск дальнейших искусственных тестов
сохраняется при уже описанной изоляции. Полный сайт/Битрикс/партнёрские доставки
и production parity пока не восстановлены. Согласия, Direct fallback, заморозки,
многополучательность, onloader ownership и end-to-end delivery остаются следующими
тестовыми сценариями, а не предварительным запретом выполнять тесты.
