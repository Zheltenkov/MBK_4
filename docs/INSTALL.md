# Установка бота на сервер МБК

Работы на сервере по этой инструкции выполняет администратор МБК.
Агент готовит и проверяет изменения локально в dev. Отправка согласовывается
с пользователем, передача идёт через MR Андрею. Прямой доступ агента
к боевому серверу запрещён правилом от 11.11.2026.

Это инструкция для того, кто ставит бота на сервер. Всё, что нужно, — сервер с
Docker и полчаса времени. Знать Python не требуется, внутрь кода лезть не
придётся.

Если что-то пойдёт не так, в конце есть раздел «Когда что-то не работает» —
там симптомы, а не коды ошибок.

---

## Коротко, что вы ставите

Бот ведёт с клиентом разговор, собирает анкету (сумма, возраст, город, долги,
работа, имущество, телефон) и передаёт результат в вашу CRM через
`classification`-эндпоинты. Решение по клиенту принимает ваш бэкенд — бот только
собирает данные и показывает клиенту ссылку, которую вы вернули.

Внутри четыре контейнера: база, разовый накат таблиц, само приложение и
веб-интерфейс. Всё поднимается одной командой и наружу не смотрит — трафик к
боту приводит ваш nginx.

Порядок вопросов и правила категорий лежат в одном файле —
`routing/matrix.yaml`. Модель их не выбирает и изменить не может.

---

## Что понадобится до начала

**Сервер.** Linux, 2 ядра, 4 ГБ памяти, 20 ГБ диска. Docker версии 24 и новее
с плагином compose (`docker compose version` должна что-то ответить).

**Доступ к Polza.ai.** Нужны API-ключ и положительный баланс организации.
Бот подключается напрямую к `https://polza.ai/api/v1`. Выберите
`MBK_LLM_PROVIDER=polza` и задайте `POLZA_API_KEY` в серверном `.env`.
Ключ кабинета используется отдельно от пароля пользователя.

В режиме Polza приложение игнорирует прежние `OPENROUTER_PROXY`, `HTTP_PROXY`
и `HTTPS_PROXY`. Qwen `qwen/qwen3.7-max`, DeepSeek `deepseek/deepseek-v4-pro`
и `deepseek/deepseek-v4.1-flash` есть в каталоге, проверенном 11.11.2026.
Назначение моделей задают `POLZA_MODEL`, `POLZA_EXTRACTOR_MODEL` и существующий
`MBK_FACT_INTERPRETATION_MODEL`. Общие настройки температуры, бюджета токенов,
сортировки провайдера и таймаута сохраняют имена `OPENROUTER_*`.

Документация сервиса — https://polza.ai/docs/glavnoe/quickstart.
Фактическая стоимость Polza указывается в рублях в кабинете и `usage.cost_rub`.
Текущий `/api/session/.../usage` показывает прежнюю ориентировочную оценку
по справочнику долларовых тарифов. Её следует читать как оценку, а списания
проверять по кабинету Polza.

**Ключ DaData** (Suggestions API). Им разбирается город и регион: от региона
зависит категория клиента. Без ключа регион не определится, и часть клиентов
уйдёт в CRM без категории.

**Ваш nginx** с настроенным HTTPS на домен, где будет висеть чат.

## Установка

### 1. Забрать код

```bash
git clone -b prod https://github.com/Zheltenkov/MBK_v4.git /opt/mbk
cd /opt/mbk
```

Ветка `prod` — та, что предназначена для боевого сервера. В ветке `master`
живёт разработка, там боевые режимы выключены.

### 2. Заполнить настройки

```bash
cp deploy/prod/env.example .env
nano .env
```

Заполнить нужно первый блок — пять значений. Они помечены в файле как
обязательные:

| Что | Откуда взять |
|---|---|
| `POLZA_API_KEY` | раздел API-ключей в кабинете Polza.ai |
| `MBK_PG_PASSWORD` | придумать любой длинный, больше он нигде не нужен |
| `MBK_AUTH_USERNAME` и `MBK_AUTH_PASSWORD` | придумать |
| `MBK_DADATA_API` | личный кабинет DaData |

Про пароль стоит сказать отдельно, потому что это неочевидно.
`MBK_AUTH_PASSWORD` заполнять обязательно, **даже если ваши клиенты приходят с
сайта и никакого пароля не вводят**. Этим паролем подписывается разрешение на
конкретный разговор — то, что не даёт постороннему открыть чужую анкету с
телефоном и суммой долга, подобрав номер сессии. Оставите пустым — чат просто
не будет создавать сессии и вернёт ошибку.

`MBK_PG_PASSWORD` надо задать **до первого запуска**. База создаётся один раз,
при первом старте, и дальше живёт со своим паролем: поменять строку в файле
потом окажется недостаточно.

При переносе работающей установки сначала обновите код бота, затем добавьте
`MBK_LLM_PROVIDER=polza` и `POLZA_API_KEY` в существующий серверный `.env`.
Сохраните прежний `.env` в закрытом каталоге администратора для отката.
Пароль БД и `MBK_AUTH_PASSWORD` сохраняются, поскольку от них зависят доступ
к данным и действующие разрешения сессий.

Для отката верните сохранённый `.env` с `MBK_LLM_PROVIDER=openrouter` и
ключом OpenRouter, затем примените обычную процедуру перезапуска backend.
На конкретном сервере используйте его действующий compose override и имена сервисов.

### 3. Запустить

```bash
docker compose -f deploy/prod/docker-compose.yml up -d --build
```

Первая сборка идёт минут пять — собирается фронтенд и ставятся зависимости.
Дальше проверьте, что всё поднялось:

```bash
docker compose -f deploy/prod/docker-compose.yml ps
```

Должно быть так: `postgres` и `backend` — `healthy`, `frontend` — `healthy`,
`migrate` — `exited (0)`. Именно `exited (0)`: это разовая задача, она накатила
таблицы и честно завершилась. Если она висит в `exited (1)` — смотрите её лог,
скорее всего дело в пароле базы.

Проверка, что бот жив:

```bash
curl http://127.0.0.1:8080/api/health
```

В ответе должно быть `"status":"ok"` и названия двух моделей — разговорной и
разбирающей реплики. Снаружи этот адрес пока недоступен, так и задумано.

Если `curl` отвечает «Empty reply from server», а контейнеры при этом
`healthy` — скорее всего в вашей сессии выставлены `HTTP_PROXY` и `HTTPS_PROXY`
(их обычно ставят как раз ради доступа к OpenRouter), и curl честно пытается
достучаться до собственной петли через прокси. Проверяйте с `--noproxy '*'`.
На работу бота это не влияет: приложение проксирует только вызовы модели.

### 4. Подключить к сайту

Бот слушает `127.0.0.1:8080` и наружу не выходит. Трафик к нему приводит ваш
nginx. Минимальный кусок конфига:

```nginx
location /chat/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Обязательно. Ответы бота идут потоком, слово за словом.
    # С включённой буферизацией клиент будет ждать молча и увидит
    # весь ответ разом в конце — выглядит как зависший чат.
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 24h;
    proxy_send_timeout 24h;
    chunked_transfer_encoding on;
}
```

Строку про `proxy_buffering off` не убирайте. Это единственное место, где чужая
настройка ломает бота не поломкой, а тем, что он выглядит медленным.

Авторизацию клиента вы делаете у себя: до бота человек доходит уже вошедшим на
сайт. У бота своего экрана входа нет, потому что `MBK_PUBLIC_CHAT=1`.

### 5. Проверить, что бот видит настоящих посетителей

Это единственный шаг, который легко пропустить и потом долго не понимать, что
случилось.

Бот считает, сколько разговоров начато с одного адреса, и после десяти в час
перестаёт открывать новые. Если он видит всех посетителей под одним адресом —
адресом вашего nginx, — то через десять диалогов чат закроется **сразу для
всех**.

За это отвечает `MBK_TRUSTED_PROXY_HOPS`. Это число прокси перед приложением,
считая nginx внутри нашего контейнера. Обычная схема «ваш nginx → контейнер»
даёт 2, и это значение стоит по умолчанию. Если перед вашим nginx есть ещё
что-то (балансировщик, CDN, Cloudflare) — прибавьте.

Как убедиться: зайдите в чат с телефона по мобильному интернету, напишите
что-нибудь и посмотрите:

```bash
docker compose -f deploy/prod/docker-compose.yml logs backend | grep "адрес посетителя"
```

Бот пишет эту строку на каждый новый разговор. В ней должен стоять адрес
вашего телефона — тот, что показывает любой сайт «мой IP». Если там
`172.х.х.х`, `10.х.х.х` или адрес самого сервера, значит бот смотрит не на то
звено: увеличьте `MBK_TRUSTED_PROXY_HOPS` на единицу и перезапустите:

```bash
docker compose -f deploy/prod/docker-compose.yml up -d backend
```

### 6. Первый лид — сначала тестовый

В `.env` есть три переключателя, отвечающих за передачу в CRM. В шаблоне они уже
в боевом положении, но начать лучше с тестового.

Поставьте:

```
MBK_CRM_SUBMISSION_MODE=test
MBK_CRM_TEST_PHONE_ALLOWLIST=79991234567
```

и перезапустите backend. В этом режиме бот отправит лид, только если клиента
зовут «Тестов Тест Тестович» и номер из списка. Всё остальное он соберёт, но не
отправит. Пройдите анкету сами до конца, проверьте, что лид появился в CRM и
поля заполнены как ожидалось.

Убедились — верните `MBK_CRM_SUBMISSION_MODE=production` и перезапустите. С этого
момента лиды создаются по-настоящему.

Если что-то пойдёт не так, поставьте `blocked`: бот продолжит работать и
разговаривать, но в CRM ничего отправлять не будет.

## Когда что-то не работает

**Клиент пишет, ответа нет, потом всё появляется разом.**
Буферизация в вашем nginx. Вернитесь к шагу 4, строка `proxy_buffering off`.

**Чат перестал открываться у всех сразу, в логе «лимит сессий».**
Бот видит всех под одним адресом. Шаг 5.

**«Не настроены MBK_AUTH_USERNAME и MBK_AUTH_PASSWORD».**
Пустой пароль в `.env`. Он нужен даже при публичном чате — см. шаг 2.

**`migrate` завершился с кодом 1.**
Не сошёлся пароль базы. Если вы меняли `MBK_PG_PASSWORD` уже после первого
запуска — старый пароль остался внутри тома с данными. Либо верните прежний,
либо, если данных ещё нет, снесите том и начните заново:
`docker compose -f deploy/prod/docker-compose.yml down -v`.
Команда с `-v` удаляет базу вместе с сессиями — на живом сервере так делать
нельзя.

**Backend в `Restarting`.**
Смотрите первые строки лога: `docker compose -f deploy/prod/docker-compose.yml logs backend | head -40`.
Чаще всего это незаполненный ключ OpenRouter или недоступный OpenRouter (нужен
прокси или шлюз — см. «Что понадобится»).

**Бот отвечает, но в CRM ничего не появляется.**
Проверьте `MBK_CRM_SUBMISSION_MODE`. В `blocked` он не отправляет ничего, в
`test` — только тестового клиента. Если стоит `production`, смотрите журнал
сбоев — он для этого и заведён:

```bash
docker compose -f deploy/prod/docker-compose.yml exec backend \
  cat logs/crm_incidents.jsonl
```

Каждая строка — один непрошедший лид: когда, какая сессия, на каком шаге и что
ответила CRM. Журнал переживает перезапуск, в отличие от `docker logs`.
Телефоны и другие длинные номера из ответа CRM в него не попадают.

**Клиенты уходят в CRM без категории.**
Не определился регион — в журнале сбоев это строки со `status: region_missing`.
Проверьте `MBK_DADATA_API` и остаток квоты в DaData. Отправку лида это не
останавливает: решение принимает ваша CRM, и лид без региона лучше потерянного
клиента.

**Ответ приходит через 20–40 секунд.**
Так бывает, когда медленно отвечает сам провайдер модели. Обычный ход — около
6 секунд, из них половина уходит на разбор реплики. Верхнего потолка на ход
сейчас нет; если это станет заметной проблемой, скажите — это чинится.

## Обслуживание

**Обновить версию:**

```bash
cd /opt/mbk
git pull
docker compose -f deploy/prod/docker-compose.yml up -d --build
```

Сессии переживут обновление — они лежат в базе, а не в памяти. Клиенты, которые
писали в момент перезапуска, увидят одну ошибку и смогут продолжить.

**Посмотреть, что происходит:**

```bash
docker compose -f deploy/prod/docker-compose.yml logs -f backend
```

**Остановить:**

```bash
docker compose -f deploy/prod/docker-compose.yml down
```

Без `-v`. С `-v` удаляются данные.

**Резервная копия базы:**

```bash
docker compose -f deploy/prod/docker-compose.yml exec -T postgres \
  pg_dump -U mbk_app mbk > /var/backups/mbk-$(date +%F).sql
```

**Доступ аналитика.** В базе есть таблица `analytics_events` — воронка разговоров
без персональных данных, связь с клиентом только по номеру сессии. Там же
лежит номер лида из CRM (событие `lead_submitted`, `payload->>'lead_id'`) —
им карточка в Битриксе связывается с разговором. Для доступа
только на чтение накатите отдельную роль:

```bash
docker compose -f deploy/prod/docker-compose.yml exec -T postgres \
  psql -U mbk_app -d mbk -v ro_password='пароль' \
  < analytics/migrations/002_analytics_readonly_role.sql
```

Пароль передаётся **без** кавычек вокруг — их psql добавит сам. Порт 5432 наружу
не опубликован, аналитик ходит SSH-туннелем.

## Что бот делает и чего не делает

**Делает:** ведёт разговор, собирает анкету, нормализует город и регион,
определяет категорию по вашей матрице, передаёт данные в CRM, показывает
клиенту ссылку, которую вернул ваш бэкенд.

**Не делает:** не советует продукты, не называет их клиенту, не принимает
решения по заявке и не обещает суммы. Всё это — на стороне вашего бэкенда.
Матрицу категорий бот применяет ровно как записано в `routing/matrix.yaml`,
и модель на неё повлиять не может.

**Персональные данные.** В зарубежную модель уходит обезличенная копия:
фамилия, телефон, точная дата рождения и адрес заменяются метками. Оригинал
остаётся на вашем сервере и попадает только в CRM. Сессия вместе с
персональными данными удаляется через 72 часа
(`MBK_SESSION_RETENTION_HOURS`).
