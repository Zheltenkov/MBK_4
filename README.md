# MBK v4 — квалификация на матрице маршрутов

Переделка MBK_v3. Что изменилось по сути: маршрут клиента выбирает не модель, а
детерминированный движок на матрице из таблицы категорий. Модель отвечает только за
человечность разговора и за разбор реплик в факты.

Результат диалога — не рекомендация текстом, а **ссылка**: бот собирает факты, отдаёт их
в маршрутизирующий микросервис и присылает клиенту персонализированный лендинг.

---

**Ставите бота на сервер МБК?** Вам нужен [docs/INSTALL.md](docs/INSTALL.md) —
пошаговая установка одной командой, подключение к nginx и что делать, когда
что-то не работает. Знать Python для этого не требуется.

**Собираетесь менять код?** Тогда [docs/HANDOVER.md](docs/HANDOVER.md):
устройство, тумблеры, особенности контракта CRM и то, что уже ломалось.

## Как это устроено

```
реплика клиента
  → локальное извлечение телефона/ДР + PII masking
  → semantic extractor (LLM)         → typed FactCandidate + evidence
  → interpretation reducer           → canonical facts + statuses/provenance
  → derive (routing/derive.py)       → факты, которые анкета не спрашивает
  → планировщик по сценарию          → следующий вопрос анкеты
  → разговорный слой (LLM, стрим)    → живой вопрос
  ...
  → анкета пройдена → движок (routing/) выбирает маршрут
  → телефон → микросервис → ссылка клиенту
```

| Модуль | Ответственность |
|---|---|
| [routing/matrix.yaml](routing/matrix.yaml) | Матрица маршрутов и порядок анкеты (`script:`). Единственный источник правды по квалификации. |
| [routing/engine.py](routing/engine.py) | Вердикт по маршрутам. Чистые функции, LLM не участвует. |
| [routing/planner.py](routing/planner.py) | Обход анкеты: что спросить следующим ходом. |
| [routing/derive.py](routing/derive.py) | Факты, которых анкета не спрашивает: кредитная история из ответов про кредиты и просрочку. |
| [routing/normalize.py](routing/normalize.py) | «1,5 млн» → 1500000, «квартира» → `flat`. |
| [interpretation/](interpretation/) | Typed-кандидаты, deterministic validation, исправления, конфликты и provenance. |
| [core.py](core.py) | Ход диалога целиком. |
| [prompts.py](prompts.py) | Персона, стиль, инструкции ходу, извлекатель. |
| [pii_masking.py](pii_masking.py) | Локальное извлечение и обезличивание outbound payload/logs. |
| [delivery/](delivery/) | Внутренний JSON и отдельный typed CRM API: qualification, realty check, lead intake. |
| [evaluation/](evaluation/) | Behavioral cases и hard checks человечности. |

Новый `interpretation/` работает в локальном runtime в режиме `semantic`:
typed extractor предлагает кандидаты, deterministic policies/reducer проверяют
их и только после этого меняют state. При timeout или невалидном JSON отдельного
хода автоматически используется legacy fallback. Решение и критерии описаны в
[ADR-0001](docs/adr/0001-deep-fact-interpretation.md).

### Ключевые решения

**Матрица — данные, не код.** Добавить маршрут, сдвинуть порог или переставить приоритет
можно правкой одного YAML, пока используются уже известные поля. Это прямо понадобится на
следующем шаге, когда в первый приоритет будут добавлены партнёры.

**Движок без LLM.** Решение о маршруте воспроизводимо и покрыто тестами. Модель не видит
ни порогов, ни приоритетов — ей незачем о них рассуждать.

**Извлечение идёт до ответа, а не после** (в v3 было наоборот, в фоне). Вопрос выбирает
движок, поэтому планировать его по фактам без последней реплики нельзя: клиент говорит
«мне 42», а бот снова спрашивает возраст. Подробнее — в шапке [core.py](core.py).

**Порядок вопросов фиксирован, приоритеты на него не влияют** (решение заказчика от
28.07.2026: «забей на приоритеты, собирай хардкор, анкету»). До этого планировщик шёл по
приоритету маршрутов и спрашивал минимум — но так разговор упирался в недвижимость первым
же содержательным вопросом и раздражал как раз тех клиентов, ради которых всё делалось.
Анкета лежит в `script:` внутри [routing/matrix.yaml](routing/matrix.yaml), рядом с
формулировками, которые она упорядочивает.

**Ветвление живёт в полях, а не в сценарии.** `after`/`after_in` у `FieldSpec` решают,
открыт ли подвопрос: «недвижимости нет» закрывает весь блок о ней, и обход сам
проваливается к авто. `after_in` нужен там, где родитель — enum: «безработный» это
непустое значение, поэтому без него у безработного спросили бы официальный доход.

**Классификатор вызывается один раз — когда анкета пройдена.** Единственное, что на него
влияет помимо фактов, — явный отказ от залога: отправлять человека на залог квартиры после
его «квартиру закладывать не хочу» нельзя. Порядок вопросов отказ при этом не меняет:
возражения отрабатываются словами, состав анкеты у всех одинаковый.

**Телефон — не шаг анкеты.** Он спрашивается после классификации, поэтому тон финальной
фразы выбирается по вердикту: маршрут найден — «пришлю ссылку», не найден — «посмотрю, что
можно подобрать», без обещаний и без отказа.

**Lifecycle явный.** `qualification → awaiting_contacts → link_ready → link_sent`; бизнес-
отказ (`no_fit`) отделён от технической ошибки (`delivery_error`). После отправки ссылки
бот не начинает квалификацию заново.

**Ссылка не проходит через модель.** Она собирается шаблоном: «поправленный» или
дописанный URL уводит клиента в никуда, и в проде это почти не отлавливается.

**Нормализатор не угадывает.** Что не распозналось однозначно — становится `None`, и бот
переспрашивает. Лишний вопрос дешевле, чем чужой маршрут из-за выдуманного значения.

**Разговорные синонимы не должны размножаться в orchestration.** Semantic extractor
предлагает каноническое значение вместе с evidence, subject и operation; reducer
проверяет контракт, но не ищет фразы по подстрокам. Семь контрастных boundary-осей
не дают смешать текущую просрочку, трудность платежей, новый заём, альтернативы,
общий залог, отдельные виды залога и цель клиента. Старый marker-based extractor
оставлен в коде как отключённый аварийный режим.

**PII маскируется до внешнего вызова.** Телефон и дата рождения извлекаются локально;
conversation model, extractor, Langfuse и новые диагностические snapshots не получают
телефон, полное ФИО или точный адрес.

## Запуск

```bash
python -m venv .venv313
.venv313/Scripts/pip install -r requirements-dev.txt
cp .env.example .env      # заполнить OPEN_ROUTER_API_KEY
.venv313/Scripts/python -m uvicorn main:app --reload
```

### Локальный интерфейс диалога

Интерфейс сохранён из MBK_v3 и адаптирован к новому контракту маршрутизации v4.
Запустите backend командой выше, затем во втором терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173` и войдите с `MBK_AUTH_USERNAME` /
`MBK_AUTH_PASSWORD` из `.env`. Vite проксирует `/api` и SSE-стрим на backend по адресу
`http://localhost:8000`; ответы ассистента идут через OpenRouter, а локальный
`MBK_ROUTER_MOCK=1` подменяет только ещё не подключённый микросервис выдачи ссылки.

Тесты (сеть не нужна):

```bash
.venv313/Scripts/python -m pytest tests -q
.venv313/Scripts/ruff check . --exclude frontend --exclude .venv313
.venv313/Scripts/pyright
```

Live behavioral regression текущей модели (использует OpenRouter и сохраняет JSON-отчёт):

```bash
.venv313/Scripts/python run_behavior_eval.py
```

Рабочий semantic-режим и диагностический shadow переключаются явно:

```text
MBK_FACT_INTERPRETATION_MODE=semantic

# либо наблюдение без влияния на рабочие facts:
MBK_FACT_INTERPRETATION_MODE=shadow
MBK_FACT_SHADOW_MAX_CALLS_PER_SESSION=5
```

В `semantic` новый reducer владеет рабочими facts, а `runtime_source` показывает
`semantic` либо `legacy_fallback`. При успешном semantic-разборе legacy не
вызывается; он запускается только после ошибки нового extractor. В `shadow` оба
контура выполняются параллельно, новый результат не влияет на диалог/маршрут/CRM
и виден только в `state.interpretation`. Подробная инструкция:
[docs/FACT_INTERPRETATION_SHADOW.md](docs/FACT_INTERPRETATION_SHADOW.md).

Ground-truth eval нового extractor:

```bash
# Только проверить 50 case-контрактов, без API:
python run_fact_interpretation_eval.py --max-cases 50

# Controlled live run: максимум 50 вызовов, один attempt на case:
python run_fact_interpretation_eval.py --live --max-cases 50 --workers 4
```

Проверка после перевода в основной контур: 50/50 основной корпус, 14/14
holdout, 8/8 исходных и 4/4 вариативных диалога.

Сквозные разговоры через тот же HTTP/SSE API, которым пользуется frontend:

```bash
# Backend должен быть запущен с MBK_ROUTER_MOCK=1.
.venv313/Scripts/python run_dialog_eval.py

# Точечный повтор только выбранных сценариев после исправления.
.venv313/Scripts/python run_dialog_eval.py --ids calm_realty_moscow emotional_debt_kazan
```

Каждый разговор сохраняется отдельным JSON: реплики, публичный state, маршрут,
причины стилистических штрафов, latency, токены и оценочная стоимость. Старая шкала
Михаила из v3 сохранена без изменения весов для исторической сопоставимости; рядом
считается адаптированная шкала v4, которая не требует называть продукт или ставку.
`run_dialog_eval.py` не вызывает CRM и в локальном контуре требует успешный
`MBK_ROUTER_MOCK`.

### CRM classification API

Контракт backend получен 23.07.2026. Три операции описаны отдельными Pydantic-моделями:
`first-qualification`, `realty-qualification`, `lead-intake`. Безопасные smoke
24.07 подтвердили обе квалификации, включая корректную обработку Москвы. Backend
дополнительно подтвердил `PHONE_DEAL`, 15-минутный дедуп и порядок отправки
незавершённых анкет. Фактическая схема, enum и lifecycle:
[docs/MBK_CRM_BACKEND_CONTRACT.md](docs/MBK_CRM_BACKEND_CONTRACT.md).
Что включено, что выключено и почему — раздел «Тумблеры» в
[docs/HANDOVER.md](docs/HANDOVER.md).

Локальный `no_fit` не считается финальным отказом: завершённая анкета всё равно
проходит `first-qualification`, после чего `lead-intake` создаёт лид даже при
`category=null`. HTTPS `thanks_url` из qualification показывается отдельной
кнопкой и никогда не проходит через LLM. Домен определяет CRM и может быть
внешним партнёрским (подтверждение backend от 24.08.2026).

**Панель разбора выключена по умолчанию.** Итоговый JSON, номер лида, режим
отправки и расход токенов живут в том же интерфейсе, что и чат клиента, поэтому
показываются только при `MBK_DEBUG_PANEL=1`. 10.08.2026 на боевом стенде клиент
увидел бы «✅ Тестовый лид создан в CRM: 3450947» и блок с JSON. Направление
умолчания важнее самой проверки: забытая переменная означает «скрыто».

Первый живой лид 10.08.2026 подтвердил весь путь: `first-qualification` вернула
`category=2217, qualified=true`, `lead-intake` создал лид. Повтор в течение
пятнадцати минут вернул тот же `lead_id` — дедуп backend работает. `thanks_url`
приходит `null`; это исходное значение CRM, а не результат фильтрации домена.
Некорректная схема или ссылка без хоста отдельно пишется в лог без пути и query.

Собственный `mbk.lead.v1` остаётся полным диагностическим JSON для локального UI:
непройденные вопросы представлены `null`. Его схема:
[docs/MBK_ROUTER_REQUEST_CONTRACT.md](docs/MBK_ROUTER_REQUEST_CONTRACT.md).

Шаблон `.env.example` по умолчанию включает безопасный локальный
`MBK_ROUTER_MOCK=1`. В production нужно явно поставить `0` и задать URL. Без URL и
без mock приложение завершает startup с ошибкой, а не выдаёт общий сайт как
персональную ссылку.

```
MBK_ROUTER_URL=https://...   # обязательно вне локального mock-режима
MBK_ROUTER_TOKEN=...
MBK_ROUTER_MOCK=1            # только явная локальная разработка
MBK_ROUTER_MAX_ATTEMPTS=2    # повторы с одним Idempotency-Key
MBK_CRM_BASE_URL=https://crm.mbk.ru/lara/api/classification
MBK_CRM_LEAD_INTAKE_ENABLED=0  # 1 создаёт реальные лиды
MBK_CRM_WORKFLOW_ENABLED=0     # 1 включает qualification → consent → lead-intake
MBK_CRM_SUBMISSION_MODE=blocked # test или production; отсутствие режима блокирует POST
MBK_CRM_TEST_PHONE_ALLOWLIST=   # обязательный allowlist для test-mode
MBK_CRM_ABANDONED_LEADS_ENABLED=0
MBK_CRM_ABANDONED_INACTIVITY_SECONDS=900
MBK_CRM_ABANDONED_SCAN_SECONDS=30
```

`PHONE_DEAL` передаётся равным `PHONE`. У CRM нет idempotency key или внешнего ID:
она только возвращает существующий `leadID` для того же телефона в течение 15 минут,
не обновляя данные лида. Поэтому приложение отправляет не больше одного lead-intake
на сессию, сохраняет `leadID`, а после timeout оставляет состояние
`outcome_unknown` без автоматического retry.

Незавершённая анкета отправляется с `UF_FROM_SITE_FILLED_OUT=0` после 15 минут без
сообщений клиента, только если уже есть телефон. `UF_SITE_AGREE_PARTNERS` полностью
отсутствует. Каждый новый ответ сбрасывает inactivity timer.

CRM-флаги по умолчанию выключены. Для локального боевого smoke одновременно нужны
`MBK_CRM_LEAD_INTAKE_ENABLED=1`, `MBK_CRM_WORKFLOW_ENABLED=1` и
`MBK_CRM_SUBMISSION_MODE=test`. Test-gate пропускает только ФИО
`Тестов Тест Тестович` и телефон из `MBK_CRM_TEST_PHONE_ALLOWLIST`; для любых
других данных CRM не вызывается и UI показывает локальный JSON. Значение
`production` снимает ограничение и предназначено только для платформы МБК.

Локальный `SessionStore` не является production-хранилищем:
на платформе состояние `crm_lead.status` и `leadID` нужно сохранять атомарно в
Redis/БД, чтобы at-most-once переживал рестарт процесса.

### DaData / ФИАС

DaData вызывается только сервером после нового ответа о городе/регионе. Однозначный
адрес получает ФИАС/ISO и класс маршрута. Для одноимённых городов бот просит клиента
подтвердить регион и не выбирает его самостоятельно.

Для `realty_list` проверяется точная пара «населённый пункт + регион» из
`routing/data/credit_club_locations.csv` (324 уникальные пары после удаления двух
регистровых дублей). Сам факт нахождения города в подходящей области недостаточен.

```
MBK_DADATA_API=...
MBK_DADATA_MAX_ATTEMPTS=1       # retry тоже расходует квоту
MBK_DADATA_REQUEST_BUDGET=8     # малый локальный лимит; production задаётся отдельно
```

Повтор одной строки берётся из LRU-кэша, а уже нормализованный адрес не запрашивается
на следующих ходах диалога.

### Аналитика событий

Одна таблица `analytics_events` в Postgres: `occurred_at`, `event`, `session_id`,
`payload jsonb`, `dedup_key`. Шесть чисел заказчика — запросы к ней, а не колонки:
счётчик-колонку нельзя пересчитать задним числом и нельзя разрезать по датам,
маршрутам и шагам анкеты.

**Персональных данных в таблице нет по контракту.** Попытка записать телефон, имя
или адрес роняет вызов (`analytics/events.py`, `PERSONAL_DATA_KEYS`) — намеренно
падает на тестах, а не маскируется молча. Связь с клиентом только через
`session_id`. Именно поэтому доступ постороннего к таблице — техническое решение,
а не решение про ПД.

Запись не роняет диалог: вставка идёт фоновым потоком через ограниченную очередь,
отказ базы логируется и проглатывается. Без `MBK_ANALYTICS_DSN` recorder выключен
и приложение работает как раньше.

Переменные окружения:

```
MBK_PG_PASSWORD=...                 # пароль пользователя приложения
MBK_ANALYTICS_DSN=postgresql://mbk_app:...@postgres:5432/mbk_analytics
```

Postgres поднимается тем же стеком и переживает обновление версии: том с
данными живёт отдельно от контейнеров.

Схему накатывает разовый контейнер `migrate` при первом запуске. Вручную
остаётся только роль для аналитика:

```
docker compose -f deploy/prod/docker-compose.yml exec -T postgres \
  psql -U mbk_app -d mbk -v ro_password='<пароль>' \
  < analytics/migrations/002_analytics_readonly_role.sql
```

Пароль передаётся **без обрамляющих кавычек**: их добавит сам psql в
`:'ro_password'`. 03.08.2026 он был передан с кавычками, они вошли в пароль, и
дата-инженер получал «password authentication failed» с виду верным паролем.

Порт 5432 наружу не публикуется — только `127.0.0.1`. Дата-инженер заказчика
подключается через SSH-туннель под ролью `analytics_ro` (только `SELECT`, только
эта таблица) и забирает данные, когда ему нужно:

```
ssh -N -L 5432:127.0.0.1:5432 <пользователь>@<адрес сервера>
psql "host=127.0.0.1 dbname=mbk user=analytics_ro"
```

Учётка аналитика заводится только под туннель: пароль заблокирован, вход
исключительно по ключу, оболочка `nologin`. Ограничения живут в
`/etc/ssh/sshd_config.d/` и проверены на живом сервере —
команды не выполняются, проброс разрешён только на `127.0.0.1:5432`, попытка
пробросить 22 или 8000 отклоняется.

Публичный ключ добавляется строкой в `~/.ssh/authorized_keys` этой учётки.
Приватный ключ генерирует он сам и нам не присылает.

Разделение зон, зафиксированное заказчиком 30.07.2026:

| Показатель | Кто считает | Событие |
|---|---|---|
| старт чата | **мы** | `chat_started` |
| количество квалификаций | **мы** | `qualification_completed` |
| собранные номера всего | CRM | — |
| подошедшие (по категории) | CRM | — |
| отправленные (по микросервису) | CRM | — |

Всё, что считает CRM, мы **не пишем вовсе**. Технически могли бы — маршрут
выбирает наш движок, ссылку запрашиваем мы, — но два источника для одного числа
не сходятся, а расхождение в отчёте потом ищут долго.

Плюс одно событие не из списка: `turn_completed` несёт номер шага анкеты. Это
наш внутренний счётчик отвала, и критерий заказчика «80% доходят до конца»
считается только по нему.

`qualification_completed` возникает, когда **анкета пройдена целиком** —
независимо от того, нашлось решение или нет. Поле `matched` в payload остаётся,
чтобы можно было разобрать инцидент маршрутизации, но это **не** «количество
подошедших»: его считает CRM по своей категории.

Брошенные анкеты отдельным событием не пишутся — выводятся запросом (сессия с
`chat_started` и без `qualification_completed`). Событие «клиент ушёл» пришлось бы
порождать по таймеру, и оно врало бы для тех, кто вернулся позже.

**Важно про откат:** том с базой живёт вне релиза, поэтому откат кода данные и
схему не откатывает.

## Доступ клиента

Стенд закрыт одним логином на всех (`MBK_AUTH_USERNAME` / `MBK_AUTH_PASSWORD`),
и это правильный режим для нас: настоящий клиент через такую форму войти не
может — регистрации нет.

В бою клиент приходит по кнопке с сайта МБК, поэтому вход открывается флагом:

```
MBK_PUBLIC_CHAT=1                     # без него чат закрыт, как сейчас
MBK_PUBLIC_CHAT_SESSIONS_PER_HOUR=10  # потолок разговоров с одного адреса
```

Открывается только `/api/session*`; список белый, поэтому новый служебный
endpoint закрывается сам. `/api/usage/global` наружу не выходит: сводный расход
по всем диалогам — наша цифра.

Потолок нужен потому, что открытый чат означает открытый расход на модель: один
диалог стоит около 3,3 ₽, и без ограничения его можно крутить в цикле.
Операторская сессия с cookie под лимит не попадает, чтобы наши прогоны в него не
упирались.

Адрес читается из `X-Forwarded-For` **справа**: заголовок накапливается слева
направо, каждый прокси дописывает адрес пира в конец и присланное клиентом не
затирает, поэтому левые элементы подделываются свободно. Сколько звеньев перед
ботом — `MBK_TRUSTED_PROXY_HOPS` (ваш nginx плюс наш внутри контейнера — это 2,
появится CDN — станет 3). Недосчитаться звена дороже, чем кажется: бот увидит
всех посетителей под адресом собственного nginx и после десяти диалогов закроет
чат сразу всем. Значение
проверяется как IP: иначе в словарь лимита попадают произвольные строки из
заголовка.

## Состояние сессий

Разговор — история, собранные факты, статус отправки лида — хранится в памяти
процесса и одновременно в таблице `sessions`. Без `MBK_SESSIONS_DSN` таблица не
используется вовсе и всё работает как раньше, только в памяти.

```
MBK_SESSIONS_DSN=postgresql://mbk_app:...@postgres:5432/mbk_analytics
MBK_SESSION_RETENTION_HOURS=72      # через сколько удалять сессию вместе с ПД
```

Зачем: рестарт backend — то есть каждая выкатка — раньше стирал все активные
разговоры, и клиент на середине анкеты получал бота, который его не помнит.
Опаснее другое. Гарантия «лид уходит в CRM один раз» держится на статусе
`not_sent → in_flight → submitted` внутри состояния сессии. Пока состояние жило
только в памяти, рестарт между `in_flight` и `submitted` терял запись — и тот же
клиент создавал в CRM второй лид.

При старте поднимаются сессии, активные за последние сутки; клиент, вернувшийся
позже, поднимается по требованию. Отдельная переменная (а не общая с аналитикой)
намеренно: базы физически одна, но включение аналитики не должно молча включать
хранение персональных данных.

`analytics_events` и `sessions` по режиму доступа противоположны. В первой ПД нет
по контракту, и роль `analytics_ro` читает её. Во второй ПД есть, и доступ туда
не выдан никому, кроме приложения; миграция дополнительно снимает права явным
`REVOKE`.

Дисковые снимки в `logs/sessions/` остались, но они для чтения человеком и
маскируют ПД — восстановление идёт не из них.

## Выкатка

Бот ставится одной командой из `deploy/prod/docker-compose.yml`: база, накат
таблиц, backend, веб-интерфейс. Пошагово — [docs/INSTALL.md](docs/INSTALL.md).

Обновление версии — `git pull` и та же команда с `--build`. Сессии переживают
перезапуск: они лежат в базе, а не в памяти процесса.
