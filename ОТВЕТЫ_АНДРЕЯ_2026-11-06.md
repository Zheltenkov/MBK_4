## 2. crm-lookup

`POST https://crm.mbk.ru/lara/api/crm-lookup`

- `Authorization: Bearer <секрет>`; предполагаемое имя переменной клиента —
  `MBK_CRM_LOOKUP_TOKEN`. Это не GitLab-токен. Значение не выводить и не
  переносить в шаблоны, память, fixture или локальные приложения заказчика.
- Тело: `phone` строкой. Входной фильтр нормализует номер в 8XXXXXXXXXX;
  валидатор требует 11 символов. Пример из справки не считать разрешённым
  реальным номером для тестового запроса.
- Общий лимит — 100 запросов за суточное окно на endpoint. Не делать запрос
  на каждый ход/каждый replan и не перебирать номера. 429 не ретраить автоматически.
- Структура: `leads`, внутри `contacts`, внутри `deals`. У лида дополнительно
  может быть собственный `deals` для сделок без контакта — подтверждено CrmLookupTree.
- `record.bitrix_id` — числовой ID лида/сделки/контакта; у `fields[]` поле
  `bitrix_id` — код свойства Битрикса. Их нельзя смешивать.
- В `fields[]`: `name`, `bitrix_id`, `type`, `value`. Пустые поля не приходят.
  Отсутствующий код не равен false/нулю/отказу. Сохранять неизвестное и типы.
- Контакт содержит ID и сделки, без собственной анкеты контактных данных.
- `{"leads": []}` означает, что в доступной выборке ничего не найдено.
  Это не доказательство, что человек новый: отдельные контакты/сделки без лида
  не возвращаются, старые лиды 2016–2019 могут не находиться.
- В исходниках подтверждены 422 `invalid_phone`, 429 `rate_limit_exceeded`
  и 502 `bitrix_error`. Авторизация выполняется middleware auth.token.

Первое внедрение — backend-клиент с ограниченным бюджетом запросов, кэшем
после проверки прав на обращение, коротким timeout и явными состояниями
found/not_found_or_outside_coverage/unauthorized/rate_limited/unavailable.
Сырые ответы не передавать целиком LLM или публичному браузеру.
Секрет/API не включён в работающего бота одним получением контракта.

**Онлоадер остаётся отдельной задачей:** сначала сервер сайта получает
сведения партнёра по защищённой связи с анкетой. Только после этого можно
использовать уже известный номер для lookup. Этот API сам номер не добывает.

## 3. Правила обычной классификации БФЛ

| Поле / условие | Подтверждено Андреем |
|---|---|
| UF_DEBT_SUMM | Сумма долга |
| UF_CRM_1452153725 | Прописка, по которой выбирается Москва/МО или регионы |
| ADDRESS_PROVINCE | Регион для кампаний партнёрки; передавать дополнительно |
| Возраст / SUMM нового кредита | Не проверяются в БФЛ-правилах |
| Обычная кредитная история | «Нет просрочек платежа» или «Есть просрочки» |
| История в виджете | «Есть просрочки» или «Готов оформить банкротство» |
| Согласие БФЛ Мск/МО и Регионы | Требуется UF_SITE_AGREE_PARTNERS; при «Нет» — КЦ |
| Кампании партнёрки | День, время, регион и признак долга от 400000 |
| Повторы/число получателей | frozen_days, duplicate_days, hands_count, delay_minutes — настраиваемые значения |

В свежем mapper признак «виджет» связан с LEAD_CHANNEL_DENIS_WIDGET.
Не переносить другой набор истории на AI-чат только потому, что у него тоже
есть виджет на странице. Не присваивать 9258/9257 по одному интересу к БФЛ.

В текущем локальном LeadIntakeRequest/mapping явного ADDRESS_PROVINCE нет.
Это конкретная задача сериализации: передать подтверждённый регион и проверить,
что downstream AddressParser не заменяет его другим адресом. Нельзя подставить
выдуманную область вместо неизвестной или смешать прописку и фактический адрес.

Порог 400000 — условие отбора кампаний, а не новый минимум для категории БФЛ.
Значения в квадратных скобках не получены: 30 дней/одни руки/фиксированную
задержку из них не выводить. Ограничения классификации и распределения раздельны.

## 4. Существующий путь долговых разделов

Свежий код подтверждает:

1. `LeadsBflController::complete` вычисляет сумму `total_credit + total_credit_pay`.
   При результате <300000 ставит отсутствие категории, иначе БФЛ Мск/МО/Регионы.
2. `LeadsBfl::mapBitrix24` сохраняет долг и ежемесячный платёж в разных полях,
   передаёт SUMM='0', IS_BFL_PRODUCT=true и UF_SITE_AGREE_PARTNERS=23000.
3. Приём идёт в `/lara/api/mbk-form/lead`, а не в `/classification/lead-intake`.
4. В legacy-контроллере для категории БФЛ используется условие
   `согласие YES ИЛИ IS_BFL_PRODUCT`. Флаг предполагает специальный уже
   согласованный процесс сайта. Его нельзя просто добавить в общий чат как
   безусловный переключатель продукта/обход вопроса о согласии.
5. Для `IS_BFL_PRODUCT + NO_CATEGORY` обычная партнёрская проверка пропускается,
   но позже контроллер всё равно может dispatch-ить SendLeadSodaTechDirect,
   если партнёрская отправка не состоялась. Поэтому нельзя заключать, что
   все 190–299 тыс. в этом пути потеряны. Надо проверить конечный Direct-outcome.

**Различие двух формул требует решения:** при долге 280000 и платеже 20000
общий классификатор относится к диапазону CPA, а анкета разделов получает
300000 и категорию обычного БФЛ. В debt-политике не объединять эти правила
молча и не выдавать ежемесячный платёж за дополнительный долг.

До изменения отправителя/endpoint нужно выбрать согласованный вариант для
AI-чата: переиспользование полного протокола разделов или адаптация с поддержкой
190–299. После выбора — fixtures и единая логика qualification/offer/consent/intake.
Кнопка «Перезвонить» в реструктуризации остаётся самостоятельной заявкой КЦ.

## 9. Результат одного локального задания сайта

Четыре искусственные БФЛ-анкеты прошли create → step → complete с настоящими
cookie/CSRF и создали четыре записи/задания. Отдельная проверка БД подтвердила
категории и исходные долг/платёж, до обработки CRM ID отсутствовали.

Один ограниченный обработчик отправил заявку в локальный Laravel CRM.
Legacy intake вернул 500: отсутствует таблица crm.b_user_group, используемая
при выборе группы 110. Осталось три pending-задания и одно failed.
У первого лида is_crm_sent=1, но crm_lead_id=NULL. Этот флаг у сайта показывает
попытку после HTTP-ответа, а не успешный приём CRM. Код ставит его до проверки
failed()/leadID; сообщения worker DONE и его exit code сами доставку не доказывают.

Реальный receiver отдельно найден и прочитан: требует Bitrix prolog_before,
модуль CRM и notifier; создание через CCrmLead::Add запускает бизнес-процессы
и роботов. Пустую reader-схему нельзя выдавать за полноценный Битрикс.
BITRIX24_URL сайта указывает на Laravel CRM, одноимённая настройка CRM — на
Bitrix receiver: это два разных назначения.

В Git подтверждены bitrix/modules/main/install/mysql/install.sql и
bitrix/modules/crm/install/db/mysql/install.sql. Поэтому причина не в отсутствии
всего SQL: требуется согласованный локальный bootstrap с совместимыми
метаданными МБК, тестовыми пользователями и управляемыми автоматизациями.
Никакие production-настройки/база/ключи не импортировались, receiver и общие
workers не запускались. Текущее покрытие и воспроизведение — dev/mbk-local/STATUS.md.

## 10. Продолжение без готовой базы Битрикса

Пользователь подтвердил отсутствие готовой обезличенной базы и инструкции.
Для тестирования приняты уровни доказательства из ADR-0002:
`docs/adr/0002-local-synthetic-write-boundary.md`.

Из установочного SQL и текущих моделей восстановлены минимальные ORM-таблицы
пользователей/групп. Структура проверена до guarded INSERT; группа 110 содержит
только явно синтетического заблокированного пользователя. Настоящий legacy
Laravel после этого дошёл до границы receiver: отдельный capture подтвердил
POST по хешу ожидаемого пути. Bitrix core этим не запускался.

Для проверки обмена подключён отдельный protocol receiver с собственным SQLite
ledger и evidence_level=protocol_simulation. Он не вызывает CCrmLead::Add.
Через настоящий сайт и Laravel CRM создана локальная protocol-запись;
сайт сохранил её ID, CRM поставила ровно одно Direct-задание с этим ID.
Direct-задание изолировано и не исполнялось; исходные очереди сохранены.
Повтор вернул тот же ID без нового dispatch. После пересоздания контейнера
приёмника и повторной операции ID, ledger и число заданий не изменились;
контейнеры трёх исходных приложений оставались теми же.

Первый сквозной запуск выявил узость начальной spec: MbkFormLeadRequest
передаёт RETURN_RESPONSE как строку "1", category — как десятичную строку.
После source/runtime сверки вход допускает эти формы, сохраняя исходные типы
для canonical hash. Ответ created остаётся строгим boolean. Исходная ошибка
422/500 и failed-задание сохранены, а не переписаны как успех.

Ещё одна подтверждённая особенность сайта: успешный retry не очищает прежний
crm_response. Исторический текст HTTP500 не является результатом последнего
успешного обмена. is_crm_sent, сохранённый ID и текст ошибки требуют отдельного
событийного учёта, а не одного общего признака «доставлено».

Это проверка протокола на искусственных данных. Настоящий Bitrix write,
workflows/robots, кампании и поставки партнёрам этим не подтверждаются.
